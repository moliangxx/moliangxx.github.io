适配器的几种写法：从灵江的 Adapter 说起

RecyclerView.Adapter 是最容易被”会用”掩盖”用对”的组件。能显示列表不算本事，面试真正会问的是：为什么 notifyDataSetChanged 差、DiffUtil 的两个回调到底怎么判、复用为什么会串图、payload 什么时候值得用、ConcatAdapter 解决什么问题。

这篇全部对照灵江项目里实际存在的 Adapter，挑 6 个有代表性的，代码位置都标出来，方便你打开项目对照。

三、灵江里的真实写法

3.1 多 ViewType：HomeFeedAdapter

首页 feed 的节点是 sealed class，四种节点对应四种 ViewType：

onCreateViewHolder 用 else -> CatalogVH 兜底，是”最后一个分支省略”的常见写法。风险是新增 ViewType 时静默创建 CatalogVH；好在 getItemViewType 已经穷尽覆盖 sealed 子类，新增节点类型会先在这里编译失败，算是有保护的。

ViewHolder 用 inner class，能直接访问 Adapter 的成员（nodes、回调），这是多 ViewType 场景的常用写法。代价是 ViewHolder 隐式持有 Adapter 引用——只要 Adapter 生命周期和 RecyclerView 一致就没问题，但如果 Adapter 是单例或长期存活，就会泄漏 ViewHolder 里的 View。

3.2 复用布局：SearchCheckinAdapter 的 5 种类型 → 3 种 Holder

搜索结果有 5 种数据类型，但只需要 3 种布局：

关键点：ViewType 和 ViewHolder 不是一一对应的。图鉴、结构、文物三种类型共用 VH.Catalog，但 ViewType 仍分开（2/3/4）。这带来一个取舍：

  • 分开 ViewType：每种类型的复用池独立，onBindViewHolder 里可以按类型精确绑定；
  • 共用 ViewType：复用池更大、内存更省，但绑定逻辑要用 when 再分一次。

灵江选了”类型分开、Holder 共用”，原因在 onBindViewHolder：三种类型虽然布局一样，但取图字段不同（galleryUrls.firstOrNull() vs imageUrl），绑定代码要分开写。

holder as VH.Checkin 这种强制转换能成立，是因为 getItemViewType 和 onCreateViewHolder 的映射关系由 Adapter 自己保证。面试里如果被问”这里为什么可以强转”，答案就是：RecyclerView 只会把对应 ViewType 的 Holder 交给 onBindViewHolder，映射错了说明 Adapter 自己有 bug。

3.4 选中态也要参与差量：ConversationAdapter

会话列表有一条”主对话恒置顶”的规则，且选中项要换背景：

这是很容易踩的坑：选中态不在数据对象里，但会影响 UI。如果 areContentsTheSame 只比较 Conversation，切换选中项时 DiffUtil 会认为”内容没变”，不触发重绑，背景就不会更新。灵江把”旧选中状态是否一致”也纳入比较，切换时只重绑新旧两行——这是正确做法。

3.5 状态最复杂的：ChatAdapter

聊天列表要处理三类东西：用户消息、AI 消息、等待气泡（loading），还要打字机动画、自动滚底、图片子列表。几个关键设计：

值得注意的四个点：

  1. distinctBy { it.id }：Room Flow 重推、云端回写都可能让同一条消息出现两次，入口先去重，DiffUtil 才不会被重复 id 搞乱。
  2. Loading 是独立行，参与 DiffUtil，areItemsTheSame 里两条 Loading 恒等。这样”等待气泡出现/消失”是标准的新增/删除，不用手动 notifyItemInserted。
  3. onViewRecycled 清理动画。AI 等待气泡里每个字都有两个 ObjectAnimator（变色 + 跳动，repeatCount = INFINITE），不复用前取消，滑出屏幕后动画仍在跑，既泄漏 CPU 又会在复用时出现残影。clearLoading() 里 animators.forEach { it.cancel() } + removeCallbacks，这是 RecyclerView 复用的标准收尾动作。
  4. boundChatId 守卫：同一消息因 Flow 重推再次 bind 时直接 return，避免打字机重播、动画重建。loadingBound 同理，防止 loading 期间重推把波浪动画反复重启。

以下均为通用示例，灵江项目中没有对应文件。

对比项 手写 DiffUtil.calculateDiff ListAdapter
计算线程 调用线程（通常主线程） AsyncListDiffer 后台线程

灵江的列表大多是单表 Flow、数据量有限，手写 DiffUtil 更直接；ChatAdapter 还需要在差量后立刻 scrollToBottom，同步语义更方便。这是”没有绝对更好，只有更合适”。

4.2 ConcatAdapter

ConcatAdapter 用来把多个 Adapter 拼成一个列表，典型场景是”头部 + 内容 + 底部”：

它解决的是”多个数据源、各自独立刷新”的问题：

  • 每个子 Adapter 自己 notifyItemChanged，不会互相影响；
  • 不需要为了 ViewType 写 0/1/2 的分支；
  • 但下标会偏移：ConcatAdapter 的 getItemViewType 会加偏移量，子 Adapter 的 ViewType 必须互不冲突，必要时用 ConcatAdapter.Config 或 isolatedViewTypes；
  • 嵌套 ConcatAdapter 会让”第几个 item”的定位变复杂，findViewHolderForAdapterPosition 拿到的位置要换算。

灵江的 HomeFeedAdapter 选择”一个 Adapter + 多 ViewType”，而不是 ConcatAdapter，原因是Banner 和模块槽位需要参与统一的 DiffUtil 计算（槽位 id 稳定、Banner 恒在首位），拆成多个 Adapter 反而不好保证插入顺序和差量身份。这是 ConcatAdapter 的边界：它适合”各段独立”，不适合”各段要按统一规则交错拼装”。

4.3 payload 局部刷新

默认的 onBindViewHolder(holder, position) 会全量重绑。如果只有一个小字段变化，可以用 payload 只更新那一块：

灵江没有用 payload：ChatAdapter 的消息内容基本是整条替换，ConversationAdapter 的选中态变化只涉及两行、重绑成本可忽略。payload 的收益只在”单行布局复杂 + 高频小改动”时成立（比如点赞、展开状态、进度条），否则增加的判断分支和维护成本不划算。

notifyDataSetChanged 为什么差，面试要答到点上：

  1. 没有任何动画，视觉上”闪一下”；
  2. 所有可见 Holder 全部重新 onBind，哪怕内容没变；
  3. 丢失滚动位置、焦点、辅助功能节点的状态；
  4. 无法区分”新增/删除/移动”，RecyclerView 的回收池和预取全部失效；
  5. 在 RecyclerView 内部会触发全量重新布局，长列表直接掉帧。

六、坑与边界

  1. areItemsTheSame 用对象相等 = 差量失效。每次 Flow 重推都是新对象，== 永远 false，DiffUtil 会认为”全删全加”，效果等同 notifyDataSetChanged。必须用业务 id。
  2. areContentsTheSame 漏掉 UI 状态。ConversationAdapter 的选中态就是例子：状态不在数据对象里，但影响显示，必须纳入比较。
  3. 复用导致状态残留。onBindViewHolder 里只设了 VISIBLE、没在另一分支设 GONE；只设了文字、没重置图片；只给部分行加了监听器。灵江的做法是每个绑定点都成对处理（bindImages 里空列表显式 GONE）。
  4. 异步图片串位。必须用 tag/请求 tag 校验，或者用 Glide 的 into(view) 自动取消旧请求。灵江自己维护 view.tag，因为要先把 imgkey/seed 解析成本地路径。
  5. 动画没有在 onViewRecycled/onViewDetachedFromWindow 取消。ChatAdapter 的无限动画是典型例子。判断标准：任何 repeatCount = INFINITE 或 postDelayed 都必须有对应的清理入口。
  6. Adapter 持有 View / RecyclerView 引用。ChatAdapter 通过 onAttachedToRecyclerView 拿 RecyclerView，又在 onDetachedFromRecyclerView 置空，并在 post 里二次校验 recyclerView === rv。不这么做，页面销毁后 post 仍然可能操作已解绑的列表。
  7. 嵌套 RecyclerView 的性能。ChatAdapter 的用户消息里嵌了一个横向 ChatImageAdapter，并设置了 isNestedScrollingEnabled = false、setHasFixedSize(true)。嵌套列表要固定高度/宽度，否则测量成本会翻倍。
  8. getItemViewType 默认返回 0。如果忘了重写，所有类型共用一个回收池，onBindViewHolder 里的 as 强转就会崩。
  9. 在 submit 里先改数据再 dispatchUpdatesTo。顺序不能反：DiffUtil 是基于旧快照算的，如果先把 items 指向新列表再 dispatch，回调里读到的已经是新数据，会出现绑定错位。灵江统一是 val old = this.nodes → 计算 → 赋值 → dispatch。
  10. notifyItemRangeRemoved(0, size) 与数据清空的顺序。ChatAdapter.clear() 先记录 size、清空列表、复位状态，再 notifyItemRangeRemoved，顺序是对的；反过来会越界。

七、面试考点

Q1：notifyDataSetChanged() 为什么性能差？

它只告诉 RecyclerView”数据全变了”，没有增量信息。结果是：所有可见 Holder 全部重绑、没有增删移动动画、回收池和预取失效、滚动位置和焦点状态可能丢失。DiffUtil 通过 areItemsTheSame / areContentsTheSame 算出最小更新集，再用 notifyItemRangeInserted/Removed/Moved/Changed 精确通知，只重绑真正变化的行。

Q2：DiffUtil 的两个回调分别怎么判？灵江怎么写的？

areItemsTheSame 判”是不是同一条”，用业务 id，比如 HomeFeedAdapter 里打卡用 item.id、图鉴用 entityId(entity)、槽位用 id；areContentsTheSame 判”内容是否相同”，直接比 data class 的值相等。特别注意 Catalog 的身份判断里带了 type，防止建筑和结构同 id 时被当成同一条。

Q3：SearchCheckinAdapter 有 5 种类型，为什么只有 3 个 ViewHolder？

因为图鉴、结构、文物共用 item_catalog 布局。ViewType 仍分 3 个（2/3/4），这样每类的复用池独立、onBindViewHolder 里可以按类型精确取图（galleryUrls.firstOrNull() vs imageUrl）；但 Holder 只需要一个 VH.Catalog。这是”ViewType 管复用池、Holder 管布局”的典型拆分。

Q4：onBindViewHolder 的 payload 重载有什么用？项目为什么没用？

payload 用于局部刷新：notifyItemChanged(pos, payload) 会把 payload 传进 onBindViewHolder(holder, pos, payloads)，可以只更新变化的那一小块，避免整行重绑。灵江的列表要么整条替换（Chat），要么只涉及两行（会话选中态），重绑成本可忽略，所以没引入。适合点赞数、展开状态、下载进度这类”单行复杂 + 高频小改”的场景。

Q5：RecyclerView 复用会导致哪些状态错乱？怎么避免？

常见四类：图片串位（异步加载回来贴到复用的 View 上）、动画残留（无限动画没取消）、可见性残留（某分支没重置 GONE）、监听器错位（闭包捕获了旧 position）。避免方式分别是：请求 tag 校验 / onViewRecycled 清理 / 每个绑定点成对设置 / 闭包捕获数据对象而不是 position。灵江的 ImageUtil.loadImage 用 view.tag，ChatAdapter 用 onViewRecycled，都是对应解法。

Q6：ListAdapter 和手写 DiffUtil 怎么选？

ListAdapter 把差量交给 AsyncListDiffer 在后台线程算，适合大数据量、频繁刷新，且不想自己维护 old/new；缺点是必须用 DiffUtil.ItemCallback，连续 submitList 的时序由框架控制。手写 DiffUtil 更可控，可以在 dispatch 后立刻做同步操作（比如 ChatAdapter 的 scrollToBottom），但要自己保证”先算后改再 dispatch”的顺序。灵江的数据量不大、且需要同步刷新，所以选手写。

Q7：ConcatAdapter 适合什么场景？有什么坑？

适合”头部 + 列表 + 底部”、”多数据源各自刷新”这类分段独立的场景。坑有三个：ViewType 会加偏移，子 Adapter 之间要避免冲突；adapterPosition 与 layoutPosition 会偏移，定位 item 要用子 Adapter 自带的方法；嵌套 ConcatAdapter 后”第几个”很难换算。灵江的 feed 需要 Banner 置顶 + 槽位按统一规则插入 + 统一 DiffUtil，分段独立反而不合适，所以用一个多 ViewType 的 Adapter。

Q8：泛型封装 Adapter 的代价是什么？

常见写法是 BaseAdapter<T> + abstract fun bind(holder, item)，减少模板代码。代价是：多一层泛型擦除和虚方法调用（业务层可忽略）、调试栈变深、不同列表的特殊需求（多 ViewType、payload、局部状态）会不断往基类里塞 if，最后基类比业务类还复杂。灵江的这些 Adapter 都各自实现（只有 Carousel 内部的 PageAdapter、ChatImageAdapter 这类嵌套场景单独处理），代码有重复但每个都能独立演进——这是”重复三次再抽象”的克制。

Q9：submit 方法里为什么必须先算 Diff 再改数据？

DiffUtil.calculateDiff 基于传入的 old / new 快照。如果先把 this.nodes 指向新列表，再在回调里读 old[oldPos]，读到的就是新数据，身份和内容判断全错。正确顺序是：保存旧引用 → 用旧引用和新列表算 diff → 更新成员 → dispatchUpdatesTo。灵江所有 submit 都是这个顺序。

Q10：Adapter 里能写业务逻辑吗？

可以写”与列表展示强相关”的逻辑（拼装、差量、滚动、复用清理），但不应该写跳转、网络请求、数据库操作。灵江的边界是：HomeFeedAdapter 负责 Banner 置顶和槽位插入（展示规则），点击只回调给 Fragment（onCheckinClick / onArchitectureClick），跳转由页面决定；ChatAdapter 负责自动滚底（展示规则），发消息由 ChatViewModel 负责。

八、一句话总结

Adapter 写法的分水岭不是”会不会 getItemViewType“，而是有没有正确的条目身份、有没有把 UI 状态纳入差量、有没有在复用时清理异步任务和残留状态——本文挑的这 6 个 Adapter 分别给出了这三点的一组答案。
