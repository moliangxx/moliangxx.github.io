枚举、const val、普通 val 与 @IntDef：灵江项目的四种”常量”取舍

“常量用枚举还是 const val？”这个问题在面试里经常被答成一句”枚举更安全”。但真实项目里，灵江同时存在四类常量：

  • M.kt 里几十个 const val 的 Int；
  • GrowthEvent 里八个 const val 的 String；
  • WeatherAlertLevel / WeatherAlertType / SeedModule 这种带属性和方法的枚举；
  • ChatFragment 里直接把选项下标映射成 Int 模式值。

它们不是风格混乱，而是每种常量承担的职责不同：有的要进数据库，有的要跨进程/跨端，有的要做 UI 展示，有的只是编译期标签。这篇按灵江真实代码逐个拆。

一、场景：一个 App 里为什么会有四种常量

先看灵江的数据模型，常量大致分四类用途：

  1. 持久化值：growth_event.type、ancient_checkin.source、architecture_part.childType 直接写进 Room 列，甚至参与复合主键；
  2. 协议/云端值：GrowthEvent.TYPE_* 会随 Bmob 上传下载，字符串必须稳定；
  3. UI 配置：WeatherAlertLevel 要带 @StringRes、要比较严重程度，SeedModule 要带 SharedPreferences key 和版本号；
  4. 纯标签/开关：M.MODE_EDIT、M.TOOL_MODE_CLOSE 这种只在进程内分派。

如果全部改成枚举，持久化列就得加 TypeConverter 或迁移；如果全部用 Int，UI 分派又会失去类型安全。灵江的选择是”按边界选方案”，下面逐个看。

2.2 GrowthEvent：const val String 作为持久化类型标签

对应文件：data/arch/local/action/GrowthEvent.kt。

为什么不是枚举？因为这一列要：

  • 写进 Room 的 TEXT 列（枚举需要 TypeConverter，还要考虑迁移）；
  • 上传到 Bmob，云端也是字符串；
  • 在服务端/开发者后台可能直接按字符串筛选。

用 const val String 的好处是”值稳定、跨端一致、零转换”；代价是类型不安全——addGrowthEventOnce(userId, type: String, ...) 接受任何字符串，写错一个字母也能入库。

2.6 ArchitecturePart.childType：常量进复合主键

对应文件：data/arch/local/part/ArchitecturePart.kt。

这一列是复合主键的一部分，已经写进了本地库、云端关系行。这种值几乎不可能改成枚举：一旦改类型，Room 要迁移、云端要改协议、历史数据要转换。能做的只有加 @IntDef 或包装类型，在编译期收窄取值范围。

2.7 ToolState.recognizeMode：Int 模式值一路泄漏

对应文件：data/ai/local/ToolState.kt、main/chat/ChatFragment.kt、agent/core/Agent.kt。

M.TOOL_MODE_* 是五个 const Int（0~4），在 ToolState、ChatFragment、Agent 之间来回传。问题是：

  • 任何 Int 都能赋给 recognizeMode，编译器不拦；
  • 两层 when 都靠 else 兜底，新增模式时不会报错；
  • “选项下标”和”模式值”是两套编号，recognizeModeAt / recognizeIndexForMode 必须手工维护映射，容易错位。

这类值最适合的是枚举 + 显式持久化 code，或者 @IntDef + 集中映射。

2.8 一个”常量与模型漂移”的真实例子

全项目搜索 CHAT_TYPE_，除了定义处没有任何引用；Chat 实体里也没有 chatType 字段（识图消息靠 imageKeys 非空判断）。常量还在，字段已经没了。

这不是要批判代码，而是提醒：常量类最容易变成”历史博物馆”。没有类型系统约束的 const，删改都没人知道。定期 grep 或改用枚举/密封模型，能自然清理这种漂移。

三、原理拆解：四种方案到底差在哪

3.1 const val：编译期内联的”字面量”

编译后大致是：

而且使用处会被内联：你在别的文件写 M.SOURCE_SYSTEM，编译进字节码的就是字面量 0，不是一次字段读取。

这带来两个后果：

  • 运行时零开销，也不需要类初始化；
  • 但改库里的 const 值，调用方不重新编译就还是旧值。这是二进制兼容性坑：SDK 升级后，App 若没重新编译，可能还在用旧常量。

const val 的限制：

  • 只能是 String 或基本类型；
  • 只能是 top-level、object 或 companion object 的成员；
  • 不能有自定义 getter，不能是 var；
  • 不能用在需要运行时计算的地方。

3.2 普通 val：运行时的静态字段 + getter

和 const 的区别：

  • 使用处是读字段/调 getter，不会内联，改值后重新编译调用方不是必须的；
  • 可以保存非基本类型、可以运行时计算、可以 by lazy；
  • 有类初始化成本；object 第一次访问会触发初始化；
  • 想暴露成 Java 的公开静态字段，可以加 @JvmField。

灵江的 M 全部用 const，是因为它们都是”真正常量”；SeedUtil 里需要运行时读 SP 的值，就只能用普通 val/函数。

3.3 枚举：固定单例 + 类

编译后是一个类，包含：

  • 三个 public static final 的常量对象（单例）；
  • 一个私有的 $VALUES 数组；
  • values()：每次调用都克隆一份数组；
  • valueOf(name)：按名字查常量，找不到抛 IllegalArgumentException；
  • ordinal 字段：声明顺序，从 0 开始；
  • name 字段：常量名。

枚举的初始化是类初始化，JVM 保证线程安全；但枚举常量构造里如果做耗时操作，会拖慢第一次访问。

3.4 @IntDef：只在编译期/lint 存在的”伪枚举”

@IntDef 是 AndroidX 注解，不是 Kotlin 语言特性。它的作用是让 lint 检查”这个 Int 只能取这几个值”：

特点：

  • 零运行时开销（SOURCE 保留策略，编译后注解不保留）；
  • 仍然是 Int，可以继续进数据库、进云端、进复合主键；
  • 但没有 when 穷尽，也没有 name/ordinal；
  • lint 能提示，运行时照样可以传任意 Int（反序列化、云端数据都可能越界）。

它适合”值已经进了数据库/协议，改不动，但想收窄编译期取值范围”的场景，正好对应灵江的 source、storageState、childType、TOOL_MODE_*。

3.6 name、valueOf 与混淆

valueOf 是大小写敏感的精确匹配，失败抛异常。它依赖常量名，所以：

  • 改名 = 改协议；
  • R8 可能混淆枚举常量名，基于 name 的持久化在跨版本时可能失效；
  • Gson 默认按字段名/枚举名序列化，也需要 keep 规则或显式 @SerializedName。

灵江的 DataShowFragment 只把 name 放在 Bundle 里（同一次进程/同一版本内使用），风险可控；但不要把这个模式复制到 SP/数据库。

3.7 枚举能带属性、方法、接口

枚举可以实现接口、可以有抽象方法（每个常量单独实现）、可以有伴生对象工具方法。它不能继承类，也不能被继承——这正好保证”常量集合固定”。

五、灵江的取舍逐条分析

5.1 哪些必须留常量

  • M.SOURCE_* / M.STORAGE_STATE_* / M.TYPE_*：都进了 Room 列，STORAGE_STATE_* 还参与同步状态机（PENDING/NORMAL/JUNK），改枚举要做 Converter + 迁移，收益不抵成本。可以用 @IntDef 在编译期收窄。
  • M.RARITY_*：稀有度对应经验值（2/5/8），是领域数值，不是标签；留 const Int 合理，但要注意它们和”档位序号”不是一回事。
  • M.DB_VERSION：注解参数，必须编译期常量。
  • GrowthEvent.TYPE_*：持久化字符串 + 云端协议，留 const String。
  • ArchitecturePart.childType 的取值：复合主键，留 const Int。
  • M.MAX_LEVEL / M.POINTS_MAX：纯数值上限，const 最直接。

5.2 哪些适合枚举

  • WeatherAlertLevel / WeatherAlertType：固定集合、带资源 id、需要 when 穷尽和严重程度比较。
  • SeedModule：模块注册表，每个模块带 spKey + seedVersion，还要当 Map key。
  • DataType（DataShowFragment）：固定两种页面类型，适合枚举；但持久化方式应从 name 改成显式 key。
  • SearchViewModel.DataType：搜索分栏类型，固定六种；虽然它和 SearchItem 的 sealed 子类有重叠，但作为”分栏标签”用枚举是合理的（详见密封类那篇）。

5.3 哪些是”该收窄但还没收窄”

  • ToolState.recognizeMode: Int：五个模式值，建议改成 enum class RecognizeMode(val code: Int)，SharedPreferences 里存 code，读的时候 entries.firstOrNull { it.code == saved } ?: CLOSE。这样 when 能穷尽，非法值有兜底，recognizeModeAt 的两套编号也能合并。
  • GrowthEvent.type: String：如果短期不能改列类型，至少加 @StringDef（AndroidX 的字符串版 @IntDef）收窄；长期看可以建一个 GrowthEventType 枚举 + name 转换，但必须先解决云端兼容。
  • M.CHAT_TYPE_*：已经没有对应字段，建议删除或补回 Chat.chatType 并真正使用，避免”注释即文档”的漂移。

5.4 一个必须说清的安全问题

const val 会被内联进调用方的字节码，APK 里必然存在明文；反编译、字符串搜索都能拿到。常量不等于安全存储。真实项目应该走服务端签发/短期 token，至少不要把长期 key 硬编码在客户端。这里把它列为”常量使用边界”，不是鼓励这么写。

六、坑与边界

6.1 const val 的二进制兼容坑

SDK/库里的 const val 改了值，调用方如果没重新编译，内联的旧值还在。App 内部模块通常一起编译，问题不大；但发布 AAR 时要特别小心，公共常量更适合普通 val 或方法。

6.2 ordinal 不能持久化

  • 重排常量 → 历史数据语义翻转；
  • 插入常量 → 后面所有值偏移；
  • 用 ordinal 做数据库列，等于把”代码顺序”写进了数据。

灵江 WeatherAlertLevel.max 用 ordinal 是进程内比较，且注释明确了严重程度顺序；但更稳的还是显式 rank。

6.3 values() 每次克隆数组

在 onBindViewHolder、循环、频繁调用的工具方法里写 values().first { ... }，会持续分配数组。改用 entries（1.9+），或把 values() 缓存成 private val ALL = values()。

6.4 name/valueOf 的协议风险

  • 枚举改名 → 持久化数据读不回来；
  • R8 混淆 → 跨版本 valueOf 可能失败；
  • 云端下发未知值 → 直接抛异常。

持久化场景用显式 code/key + firstOrNull 兜底，不要直接用 valueOf。

6.5 枚举不是”零成本”

每个常量是一个对象，类还有 $VALUES 数组和元数据。几十个常量完全无所谓；但如果是几百个、且只需要一个 Int 标签，枚举的内存和类加载成本就不划算了。

6.6 @IntDef 不是运行时约束

它只在 lint 层起作用。云端返回 source = 99，@ImageSource 依然接受，when 也会走 else。所以 @IntDef 必须配合运行时兜底：

灵江 ToolStateRepository.normalizeMode 做的就是这件事：if (mode in M.TOOL_MODE_CLOSE..M.TOOL_MODE_RELIC) mode else M.TOOL_MODE_CLOSE。范围校验能挡住越界，但挡不住”范围内但语义错误”的值（比如把 TOOL_MODE_RELIC 传给 source）。

6.7 同一个 Int 域被多个语义复用

SOURCE_SYSTEM = 0、STORAGE_STATE_JUNK = 0、TOOL_MODE_CLOSE = 0 都是 0。函数签名只写 Int 时，传错常量完全合法。@IntDef 的价值就在这里：让 lint 区分不同”Int 域”。

6.8 枚举在 when 里加 else

和 sealed 一样，加 else 就放弃”新增常量编译报错”的保护。只有确实需要兜底（比如未来常量来自服务端）时才加。

七、面试考点（问答式）

Q1：const val、普通 val、枚举、@IntDef 怎么选？

A：先看值要不要跨边界持久化。要进 Room/云端/注解 → const val（值稳定、编译期常量）；只是运行时配置、非基本类型 → 普通 val；集合固定且需要类型安全、when 穷尽、带属性/方法 → 枚举；值已经进了历史数据改不动，但想收窄编译期范围 → @IntDef。灵江的 DB_VERSION 是注解参数只能 const，WeatherAlertLevel 是固定集合用枚举，source 已进库用 const Int + 可加 @IntDef。

Q2：const val 和普通 val 的编译产物有什么区别？

A：const val 是编译期常量，使用处内联成字面量，运行时零读取；普通 val 是静态字段 + getter（object 里）或实例字段，使用时真正读字段。const 只能基本类型/String、不能自定义 getter；普通 val 可以运行时计算、可以是非基本类型。const 改值后调用方不重编译会保留旧值，这是二进制兼容坑。

Q3：为什么 ordinal 不能持久化？

A：ordinal 是声明顺序，不是稳定业务 id。重排/插入常量会让所有后续值偏移，历史数据读出来就变成另一个语义。持久化应该存 name（仍有改名/混淆风险）或显式 code（最稳）。灵江 WeatherAlertLevel.max 用 ordinal 只做进程内优先级比较，且顺序有业务含义，属于可接受用法。

Q4：values() 和 entries 有什么区别？

A：values() 每次调用返回一个新克隆的数组，有分配开销，且数组可变（改了也不影响枚举）；entries（Kotlin 1.9+）返回缓存的不可变 EnumEntries 列表，不克隆，推荐遍历/查找。enumValues<T>() / enumEntries<T>() 是它们的泛型版本。高频路径不要反复 values()。

Q5：枚举的 when 为什么能穷尽？编译成什么？

A：编译器知道枚举的常量全集，when 必须覆盖每个常量（或有 else），新增常量会让所有穷尽 when 编译失败。JVM 上通常编译成基于 ordinal 的 tableswitch；跨模块时可能生成一个 $EnumSwitchMapping 映射数组，把当前编译期的 ordinal 映射到分支。它比 sealed 的 instanceof 链更适合”纯标签分派”。

Q6：枚举能不能带属性、方法、实现接口？能不能继承？

A：可以带构造参数/属性、成员方法、伴生对象方法，可以实现接口，甚至每个常量可以有自己的抽象方法实现。不能继承别的类，也不能被继承——这正是”常量集合固定”的保证。灵江 WeatherAlertLevel(titleRes)、SeedModule(spKey, seedVersion) 都是这种用法。

Q7：枚举和密封类什么时候互换？

A：枚举适合”固定单例 + 所有常量字段结构相同 + 需要 name/ordinal/values”；密封类适合”每个变体携带不同类型/数量的数据 + 需要 data class 的 copy/equals”。灵江 DataType（纯标签）用枚举，SearchItem（每个变体带不同实体）用密封接口。如果密封类的子类全是无字段的 object，可以降级成枚举；如果枚举需要给不同常量挂不同字段，说明该换密封类。

Q8：@IntDef 的原理和局限？

A：它是 AndroidX 注解，@Retention(SOURCE) 时编译后不保留，运行时零开销；lint 检查注解标注的参数/返回值只能传指定常量。局限是：只在编译期/lint 生效，运行时任意 Int 都能进来；没有 when 穷尽；不能遍历；反序列化/云端数据仍要运行时兜底。它最适合”历史 Int 列不能改类型，但想减少传错常量”的场景。

Q9：为什么 DB_VERSION 必须是 const val？

A：Room 的 @Database(version = ...) 是注解参数，Java/Kotlin 注解参数要求编译期常量。普通 val 不是编译期常量，编译不过。const val 还能保证”关于页展示的版本号”和”注解里的版本号”同源，灵江 AboutFragment 直接读 M.DB_VERSION。

Q10：混淆/R8 对枚举有什么影响？

A：R8 可能对枚举做 unboxing 优化（把枚举替换成 int），但一旦代码用了 values()/valueOf()/name() 或反射，优化会受限；枚举常量名可能被混淆，基于 name 的持久化/Gson 序列化跨版本会失效，需要 keep 规则或 @SerializedName。值内联的 const val 不受改名影响，但明文密钥仍能被反编译看到。

八、一句话总结

常量方案的选择不是”安全 vs 不安全”，而是”这个值要不要跨进程/跨版本/跨端”：跨边界就用稳定的 const/显式 code，进程内固定集合就用枚举换类型安全和穷尽，历史 Int 列用 @IntDef 收窄但不能当运行时校验。
