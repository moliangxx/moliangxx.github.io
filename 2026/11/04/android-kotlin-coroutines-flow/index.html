协程与 Flow：灵江项目里的搜索防抖、聊天发送与 Room 订阅

协程的面试题很容易变成名词默写：launch、async、withContext、SupervisorJob、StateFlow……但真实项目里，决定代码对不对的往往不是”知不知道这个 API”，而是：

  • 这个 launch 应该挂在哪个作用域？
  • 取消之后，catch (e: Exception) 会不会把取消也吞掉？
  • 为什么搜索结果用 StateFlow，而”回前台补查”用 SharedFlow？
  • Room 的 Flow 到底在哪个线程查、哪个线程收？

这篇全部对照灵江项目 d:\AndroidProject\LingJiang 的真实代码（路径相对 app/src/main/java/com/lingjiang/），把协程讲成”一套有生命周期、可取消、结构化的工作管理方式”。

一、场景：灵江里协程出现的五个位置

  1. 搜索防抖：输入 300ms 后才查，点搜索按钮要立刻取消防抖任务；
  2. 聊天发送：落库用户消息 → 调 AI → 落库回复，期间要防止重复发送；
  3. 首页/我的页订阅：Room Flow 在页面可见时收集，不可见时停止；
  4. 网络请求：Retrofit 的 suspend 接口、Bmob 回调转挂起函数；
  5. 进程级定时任务：天气预警每 N 秒轮询，回前台补查。

每一处都在回答同一个问题：这段工作活多久、谁取消它、失败了谁负责。

对应文件：main/home/HomeFragment.kt。

这行代码做了三件事：

  1. 页面进入 STARTED 时启动收集；

  • Mutex：轮询和回前台补查串行化，避免并发重复提醒；
  • MutableSharedFlow(extraBufferCapacity = 1)：事件信号，连续触发可合并；
  • while (isActive) { ...; delay(...) }：可取消的循环，不是死循环。

2.15 UserRepository.ioScope：一个”应用级”作用域

对应文件：data/user/UserRepository.kt。

ioScope 没有 Job/SupervisorJob，也没有取消入口，生命周期等于进程。它比 GlobalScope 好一点（至少类型明确、不是全局单例），但仍有同样的问题：异常会走默认处理器，可能崩溃；任务无法取消。

三、原理拆解

3.1 协程不是线程

协程是可挂起的计算，线程是执行载体：

  • 一个线程可以跑很多协程；
  • 一个协程可以在不同线程上继续执行（取决于调度器）；
  • 协程挂起时，线程被释放去干别的，不是”线程睡着等”。

所以 viewModelScope.launch 默认跑在 Main，但里面调 withContext(Dispatchers.IO) 的数据库查询会切到 IO 线程池；查询返回后，协程回到 Main 继续更新 UI。

3.2 挂起不等于切线程

suspend 函数的编译产物是状态机 + CPS：

挂起只是”保存现场并返回”，是否切线程由 Dispatcher 决定：

  • delay(300) 在 Main 上挂起，300ms 后仍在 Main 恢复（除非中途 withContext）；
  • Retrofit 的 suspend 在 OkHttp 回调线程恢复，然后由协程的 dispatcher 派发回原线程；
  • withContext(Dispatchers.IO) 是显式的”切线程 + 挂起”。

3.3 结构化并发

launch 返回 Job，Job 有父子关系：

  • 父协程结束前会等待所有子协程；
  • 父协程取消会取消所有子协程；
  • 子协程失败会取消父协程（除非 SupervisorJob/supervisorScope）。

viewModelScope 的上下文是 SupervisorJob() + Dispatchers.Main.immediate：

  • SupervisorJob：一个子协程失败，兄弟不被取消；
  • Main.immediate：如果已经在 Main，直接执行，不额外 post 一次；
  • 生命周期绑定 ViewModel.onCleared()。

3.4 launch、async、withContext

API 返回 用途 异常行为
launch Job 不关心结果的后台工作 异常交给 CoroutineExceptionHandler/线程默认处理器；没有则崩溃
async Deferred<T> 需要结果/并行 异常存进 Deferred，await() 时抛出；普通作用域下失败也会取消父/兄弟
withContext 直接返回结果 切调度器 + 串行执行 异常直接向上抛，取消父协程

withContext 不是”启动一个新协程不管了”，它会挂起当前协程直到块执行完，并把结果返回。

3.5 Flow：冷流与热流

  • 冷 Flow（flow { }、Room 的 Flow<T> 查询）：每次 collect 都重新执行，没有订阅者就不工作；
  • 热 Flow（StateFlow、SharedFlow）：一直存在，订阅者可有可无，值由外部写入。

Room 的 Flow 是冷流 + InvalidationTracker：收集时注册表变更监听，表变了就重新查询并发射。离开页面取消收集，监听也注销。

3.6 StateFlow、SharedFlow、LiveData

维度 StateFlow SharedFlow LiveData
初始值 必须有 没有（可空） 可以没有
重放 固定 replay=1 可配置 replay 持有最后值
合并 默认 conflated（只保留最新） 默认不合并，可配 buffer 主线程 setValue，天然”最后值”
去重 内置 distinctUntilChanged 不自动去重 不自动去重
生命周期 需配合 repeatOnLifecycle 同左 原生 lifecycle-aware
线程 任意线程写 value 任意线程 emit setValue 主线程，postValue 任意线程
适用 UI 状态 事件/信号 传统观察者、Java 互操作

灵江的对应：

  • SearchResult、isLoading、wallpapers → StateFlow（UI 状态，永远有值）；
  • foregroundSignal → SharedFlow（事件，不需要重放历史）；
  • UserDao 的查询、login() 的 MutableLiveData → LiveData（历史代码/传统观察）。

3.7 repeatOnLifecycle 与 flowWithLifecycle

写法 作用范围 适合
repeatOnLifecycle(STARTED) { ... } 整个块，可以包含多个 launch/多个 Flow 多个 Flow 共享生命周期
flowWithLifecycle(flow, STARTED) 单个 Flow 只订阅一个 Flow

flowWithLifecycle 是操作符，等价于”这个 Flow 只在生命周期内收集”；repeatOnLifecycle 是块级 API，块内可以起多个子协程。灵江 ChallengeFragment 三个 Flow 用 repeatOnLifecycle 是合理的；如果只有一个 Flow，flowWithLifecycle 更简洁。

3.8 collectLatest、debounce、flatMapLatest

  • collect：顺序处理每个值，处理慢会积压（对 conflated 的 StateFlow 则只保留最新）；
  • collectLatest：新值来了取消上一个处理块，适合”渲染/动画/请求”只关心最新；
  • debounce(300)：上游快速发射时，静默 300ms 后才放行最后一个；
  • flatMapLatest { query }：每个新 query 取消上一个内层 Flow（搜索竞态的标准解法）。

灵江的搜索防抖是手写 delay + Job.cancel，等价于 debounce；但没有用 flatMapLatest，因为查询是 suspend 函数而不是 Flow。

3.9 异常传播

  • launch 的异常：如果没人 catch，且作用域是 SupervisorJob，异常会交给 CoroutineExceptionHandler；没有 handler 就到线程默认处理器，Android 主线程上通常表现为崩溃。
  • async 的异常：存进 Deferred，await() 时抛出；在普通 coroutineScope 里，失败也会取消兄弟协程。
  • withContext 的异常：直接抛给调用方。
  • supervisorScope：子协程失败不影响兄弟，也不会取消父；每个子协程要自己 catch。

3.10 取消是协作式的

job.cancel() 只是把 Job 标记为取消，真正停止要等协程执行到挂起点或检查 isActive：

  • delay、withContext、Room/Retrofit 的 suspend 调用都是挂起点，会响应取消；
  • 纯 CPU 循环如果不检查 isActive，cancel() 不会立刻停；
  • cancel() 不等待结束，要等结束用 join()；
  • 取消时抛的是 CancellationException，它是”正常控制流”，不应该当成业务错误。

  • 没有 SupervisorJob：一个任务失败可能影响作用域；
  • 没有 CoroutineExceptionHandler：未捕获异常会崩；
  • 没有取消入口：进程结束才停。

5.4 为什么这里要用 viewModelScope 而不是 GlobalScope

以 ChatViewModel.sendMessage 为例：

  1. 生命周期：用户退出聊天页/ViewModel 清除，正在等待的 AI 回复应该取消，viewModelScope 自动做；GlobalScope 不会，协程会继续持有 chatList、repository 等引用。
  2. 线程：viewModelScope 默认 Main，_isLoading.value、chatList.value 的读写天然在 UI 线程；GlobalScope 默认也是 Main？GlobalScope.launch 默认 Dispatchers.Default，不是 Main。要写 UI 状态还得手动切。
  3. 异常：GlobalScope 的异常没有父作用域接管，直接走全局处理器，容易崩；viewModelScope 至少是 SupervisorJob，兄弟任务不受影响，也方便加 handler。
  4. 可测试性：viewModelScope 可以替换 Main dispatcher 做测试；GlobalScope 难控。
  5. 结构化并发：viewModelScope 的子任务随 ViewModel 一起取消；GlobalScope 是”发射后不管”。

一句话：和界面状态绑定的工作，生命周期就应该是界面的；只有确实要活过界面的工作，才配用应用级作用域，而且要有 SupervisorJob + 异常处理 + 取消策略。

5.7 stateIn 的 WhileSubscribed(5000) 与 lateinit

chatList 是 lateinit，loadChatHistory 每次重新赋值一个新的 StateFlow。旧的 stateIn 上游在最后一个订阅者离开后还会活 5 秒；如果 Fragment 不取消旧收集，可能出现两条流同时推给适配器。灵江在 observeChatList() 里先 chatCollectJob?.cancel()，这是必要的。

5.8 collectLatest 不是”取消上游”

collectLatest 只取消处理块，不会取消生成值的 Flow。如果处理块里有 repository.addChat 这种写操作，新值来了可能把上一次写操作取消一半。灵江这里块内是同步 UI 提交，所以安全；换成”收集后发请求”就要小心。

5.9 SharedFlow 的事件可能丢

foregroundSignal = MutableSharedFlow<Unit>(extraBufferCapacity = 1)：

  • replay = 0：没有订阅者时发射的值不会保留；
  • extraBufferCapacity = 1：有订阅者但处理慢时，最多缓冲一个；
  • 如果持续发射超过缓冲，tryEmit 可能失败/丢弃。

灵江同时有轮询兜底，所以丢一两个”回前台信号”不影响正确性；如果是”支付成功”这种不可丢事件，应该用 replay 或 Channel/持久化。

5.10 Room suspend 已经不在主线程

Room 的 suspend DAO 查询由 Room 自己的查询执行器执行，不需要在仓库层再包一层 withContext(Dispatchers.IO)；包了也不会错，只是多一次调度。Flow 查询同理，InvalidationTracker 在 Room 的执行器上重新查询，收集方只负责消费。

六、面试考点（问答式）

Q1：协程和线程是什么关系？协程是轻量级线程吗？

A：协程是可挂起的计算单元，线程是执行载体。一个线程可以跑多个协程，协程挂起时释放线程；协程不是线程，也不等于线程池任务。说”轻量级线程”只是类比，容易误导——协程的调度仍依赖线程/调度器，Dispatchers.Main 最后还是落在主线程。

Q2：挂起函数会切换线程吗？

A：不一定。挂起只是保存现场并返回，是否切线程由 Dispatcher 决定。delay 在 Main 挂起后仍在 Main 恢复；withContext(Dispatchers.IO) 才是显式切线程；Retrofit 的 suspend 在 OkHttp 回调线程恢复，再由调度器派发回原上下文。判断”在哪个线程”看 dispatcher，不是看有没有 suspend。

Q3：launch、async、withContext 有什么区别？

A：launch 返回 Job，不关心结果，异常按作用域规则处理；async 返回 Deferred<T>，用 await() 取结果，异常在 await 抛出（普通作用域下失败也会取消父/兄弟）；withContext 切调度器并挂起等待结果，异常直接向上抛。并行用 async，串行切线程用 withContext，发射后不管用 launch。

Q4：结构化并发是什么？viewModelScope 和 GlobalScope 差在哪？

A：结构化并发是”父协程负责子协程的生命周期”：父等子结束、父取消子、子失败按规则影响父。viewModelScope 绑定 ViewModel，清除时自动取消，默认 Main，适合 UI 工作；GlobalScope 没有父、不可取消、异常走全局处理器、默认 Default 线程，容易泄漏和崩溃。所以灵江的聊天发送用 viewModelScope，登录恢复用户这种应用级工作才用仓库自己的 ioScope。

Q5：SupervisorJob 和普通 Job 的区别？viewModelScope 里子协程异常会怎样？

A：普通 Job 下，一个子协程失败会取消父和兄弟；SupervisorJob 下，子失败不影响兄弟和父。viewModelScope 用的是 SupervisorJob，所以一个 launch 崩了不会取消其他 launch；但异常本身仍会交给 CoroutineExceptionHandler，没有 handler 就到线程默认处理器，Android 主线程上通常崩溃。async 的异常先存进 Deferred，await 时抛出。

Q6：StateFlow、SharedFlow、LiveData 怎么选？

A：StateFlow 是”有当前值、只保留最新、自动去重”的热流，适合 UI 状态；SharedFlow 是”事件流”，可配置 replay/buffer，适合一次性事件/信号；LiveData 是 Android 传统可观察数据，生命周期感知、主线程 setValue，适合与旧代码/Java 互操作。灵江搜索结果/加载态用 StateFlow，回前台补查信号用 SharedFlow，用户查询和登录结果还有 LiveData。

Q7：repeatOnLifecycle 和 flowWithLifecycle 有什么区别？

A：repeatOnLifecycle(state) { ... } 是块级 API，进入状态启动块、离开取消块，块内可以 launch 多个 Flow；flowWithLifecycle(flow, state) 是操作符，只作用于一个 Flow。两者都比 launchWhenStarted 好：后者只是挂起收集协程，不取消上游，页面不可见时上游可能继续工作。灵江 ChallengeFragment 三个 Flow 用 repeatOnLifecycle。

Q8：collect、collectLatest、debounce、flatMapLatest 的区别？

A：collect 顺序处理每个值；collectLatest 新值来时取消上一个处理块（不取消上游）；debounce 静默一段时间只放行最后一个上游值；flatMapLatest 每个新值取消上一个内层 Flow，常用于搜索请求防竞态。灵江搜索是手写 Job.cancel + delay，等价于 debounce。

Q9：协程异常怎么传播？CoroutineExceptionHandler 什么时候生效？

A：launch 的未捕获异常交给 CoroutineExceptionHandler（如果作用域/启动参数里有），否则走线程默认处理器；async 的异常存进 Deferred，await 时抛出；withContext 直接抛给调用方。CoroutineExceptionHandler 只对”根协程”生效，子协程的异常会先向上传播；async 不用它，因为异常在 Deferred 里。

Q10：supervisorScope 和 coroutineScope 的区别？

A：coroutineScope 里任一子协程失败，整个作用域取消，兄弟一起取消；supervisorScope 里子失败不影响兄弟和父，每个子要自己 catch。灵江搜索目前是串行，没有用 supervisorScope；要改成并行且允许单条失败，就用它。

Q11：cancel() 之后代码会立刻停吗？怎么正确取消？

A：不会立刻停。取消是协作式的，协程要执行到挂起点或检查 isActive 才停。delay、withContext、Room/Retrofit 的 suspend 调用会响应取消；纯 CPU 循环要手动 ensureActive()。cancel() 不等待结束，需要等待用 join()。取消抛 CancellationException，必须继续向上抛，不能当业务错误吞掉。

Q12：stateIn 的 SharingStarted 三种策略有什么区别？

A：Eagerly 立即启动上游、永不因无订阅者停止；Lazily 第一个订阅者到来才启动，之后不停止；WhileSubscribed(stopTimeout) 有订阅者才启动，最后一个订阅者离开后等 stopTimeout 再停。WhileSubscribed(5000) 适合 UI，给配置变化留缓冲；灵江 chatList 就用它。

Q13：Room 的 Flow 为什么能自动刷新？在哪个线程查？

A：Room 的 Flow 查询由 InvalidationTracker 支持：收集时注册表变更观察，表变了就重新执行查询并发射。查询在 Room 的查询执行器上跑，不在收集方线程；收集方通常在 Main，只做 UI 更新。Flow 是冷流，无人收集就不查；离开页面用 repeatOnLifecycle 取消收集，监听也会注销。

七、一句话总结

协程的核心不是”会写 launch”，而是”给每段异步工作找对生命周期和取消边界”：UI 工作绑 viewModelScope，跨页面工作用带 SupervisorJob 的应用级作用域，Flow 在 repeatOnLifecycle 里收集，取消异常永远要重抛。
