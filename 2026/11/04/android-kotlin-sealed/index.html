密封类：从灵江的联合模型说起

面试里问 sealed，标准答案是”受限的类层次结构，when 可以穷尽”。这句话不算错，但它解释不了三个更关键的问题：

  • 为什么灵江的搜索项用 sealed interface，首页节点却用 sealed class？
  • 明明用了 sealed，为什么 HomeFeedAdapter 里还有 else 和 as?？
  • 新增一种类型时，编译器到底能帮你拦住几处？

这篇全部对照灵江项目 d:\AndroidProject\LingJiang 的真实代码（下文路径相对 app/src/main/java/com/lingjiang/），把 sealed 讲成”一个用来描述’有限种可能’的工具”，而不是语法知识点。

一、场景：一个列表要装下五种东西

灵江的搜索页有两级：

  • 一级是综合候选列表，里面可能混着打卡、古建图鉴、结构、文物、用户；
  • 二级是六个分栏，每个分栏只放一种类型。

如果按 Java 的老办法，通常是一个 SearchItem 基类 + 一个 int type 字段：

调用方拿到 item 后要先判断 type，再 (AncientCheckin) item.data。问题有三个：

  1. type 和 data 可以不同步，编译器不管；
  2. 新增类型时，所有 switch 都不会报错，只是默默走 default；
  3. 强转写错只会在运行时炸。

灵江的做法是把”类型”和”载荷”绑死在一个密封层次里。

三、原理拆解：sealed 到底封闭了什么

3.1 本质：编译器可见的”直接子类清单”

sealed class / sealed interface 会把自己的直接子类记录在 Kotlin 元数据里。编译器在处理 when 时，拿到这份清单，逐个检查分支是否覆盖。

所以：

  • 穷尽检查发生在编译期，运行期没有额外校验；
  • 编译器只要求覆盖直接子类；如果某个子类本身是抽象的，用 is 子类 一个分支就能覆盖它下面所有具体类；
  • 新增直接子类，所有对密封类型做 when 表达式的地方都会编译失败（这是它最大的价值）。

3.2 子类能写在别的文件吗？

这是面试高频题，答案要带版本：

Kotlin 版本 直接子类的限制
1.5 之前 必须和密封类同一个文件
1.5 及之后 必须在同一个包、同一个模块（同一个编译单元）
所有版本 间接子类（孙子类）不受 sealed 规则约束

所以”sealed 的子类必须同文件”是旧答案。现在可以拆文件，但不能跨模块。

这带来一个真实的工程约束：如果 sealed 基类放在 :core 模块，业务模块 :app 不能新增子类。想扩展，要么把新子类也放进 :core，要么把基类下沉到能同时被两边看到的模块。灵江是单模块应用，所以 SearchItem、HomeFeedNode 可以随便放在各自文件里。

3.3 嵌套 vs 平铺

灵江两种都用了：

  • SearchItem 的子类嵌套在接口体内（SearchItem.CheckinItem）；
  • HomeFeedNode 的子类也嵌套；
  • SearchCheckinAdapter.Row 的子类平铺在同一个文件（CheckinRow、ArchitectureRow…）。

选择依据是作用域和复用范围：

写法 优点 代价
嵌套在 sealed 体内 命名空间干净，SearchItem.CheckinItem 一看就知道归属；天然满足同文件限制 名字较长；外部要带外层前缀
平铺同文件/同包 名字短；适配器内部行模型读起来轻 容易和别的模型重名；需要靠包/文件组织

一个实用规则：只在当前类内部用的行模型，用 private sealed interface + 平铺/嵌套都行；被多个文件引用的领域模型，用 top-level sealed + 嵌套子类。

3.4 sealed class 与 sealed interface 怎么选

维度 sealed class sealed interface
能否有构造参数/共享状态 可以 不可以（接口无 backing field）
能否有 protected 成员 可以 不能（接口成员默认 public）
子类是否已继承别的类 不可以（单继承被占用） 可以（接口可多实现）
能否有抽象属性 可以 可以
默认构造可见性 protected（外部不能 new） 无构造
适用场景 需要共享字段/模板方法 只需要”固定实现集合”，子类各自带数据

灵江的选择是合理的：

  • SearchItem / Row：子类都是 data class，各自持有不同实体，没有共享状态 → sealed interface；
  • HomeFeedNode：四种节点同属一个页面模型，未来可能加共享行为/字段 → sealed class（当前其实两种都能写）。

3.5 和枚举、抽象类、普通接口的区别

类型 实例数量 子类/实现范围 when 穷尽 每个变体能否带不同数据
enum class 固定常量，单例 不能继承，不能外部新增 能 不能（所有常量字段结构相同）
sealed class/interface 由子类决定，可有多个实例 同包同模块 能 能（每个子类字段不同）
abstract class 由子类决定 任意模块 不能（必须 else） 能
普通 interface 由实现决定 任意模块 不能（必须 else） 能
基类 + Int type 由调用方决定 任意 不能（判的是 Int） 能，但类型不安全

一句话：枚举是”有限个单例”，sealed 是”有限个类型”，抽象类是”开放的类型”。

3.6 when 穷尽后编译成什么

对密封类型，when 没有 ordinal 可用，编译器生成的是一串 instanceof 判断（JVM 上就是 instanceof + checkcast）。它不是反射，也不是哈希表，和手写 if (x instanceof A) 基本等价。

对枚举，when 会编译成基于 ordinal 的 tableswitch（跨模块时还会生成一个 $EnumSwitchMapping 映射数组）。这也是枚举分派通常比 sealed 稍快的原因，但在 Android 列表/页面分派这种量级上，两者都不是瓶颈。

3.7 可空与 when 语句的穷尽

两个容易忽略的边界：

  • 密封类型可空时，null 是一个额外分支，不能省；
  • Kotlin 1.7 起，对 sealed / enum / Boolean 的 when 语句也要求穷尽（以前只有表达式要求）。所以”我只是拿 when 当 if-else 用，不赋值”也不能漏分支了。

四、写法对比：同一个需求，五种落地

以”搜索结果项”为例：

写法 代码形态 类型安全 新增类型时编译器提示 适用
sealed interface + data class 当前灵江写法 强 所有 when 报错 变体带不同实体、需要穷尽
sealed class + data class 与上面几乎等价 强 所有 when 报错 需要共享状态/构造/模板方法
enum + Any 载荷 enum Type { CHECKIN... } + data: Any 弱（要强转） 分派处报错，但载荷仍不安全 变体只有标签、没有不同数据
基类 + Int type SearchItem(type, data) 最弱 不报错 遗留代码、跨语言/跨进程 DTO
普通接口 + kind 字符串 interface Item { val kind: String } 中（无强转但开放） 不报错 允许外部插件扩展

灵江同时在用前两种和最后一种：SearchItem 用 sealed interface，HomeFeedNode 用 sealed class，HomeFeedModule 用普通 interface。不是风格不统一，而是”集合是否封闭”这个业务事实不同。

五、坑与边界

5.1 密封类不是运行时安全

sealed 的约束是编译器层面的。JVM 上它仍是一个普通类/接口，Kotlin 编译出的构造器是 protected，理论上同包的 Java 代码或反射仍能绕开。不要拿 sealed 当安全边界，它只是编译期契约。

5.2 多模块是硬墙

前面说过：直接子类必须同模块。Android 工程一旦拆模块，把 sealed 基类放错位置，业务模块就永远加不了新子类。这不是”配置问题”，是语言规则。

5.3 序列化：Gson 不认识 sealed

灵江的 sealed 模型只在本进程内流转，没有直接走网络/数据库。如果要把 sealed 存起来，注意：

  • Gson：默认按声明类型反序列化，子类特有字段会丢；需要 RuntimeTypeAdapterFactory 或自定义 JsonAdapter，并显式写类型判别字段。
  • kotlinx.serialization：@Serializable 的 sealed 类支持多态序列化，默认判别字段名是 "type"，每个子类也要 @Serializable。
  • Room：@Entity 不能是 sealed 类本身；灵江的做法是”表里存 Int/String 类型标签 + 各实体独立表”，这其实回到了 2.5 的 type + entity 模式。要在 Room 里保留 sealed 的 type safety，需要在 DAO 层做”标签 → 子类”的映射，并保证映射也是穷尽的。
  • Parcelable：@Parcelize 要加在每个具体子类上，基类只作为类型声明。

5.4 混淆/R8

  • 基于类名的多态序列化（Gson RuntimeTypeAdapterFactory、手写 Class.forName）会被混淆破坏，需要 keep 规则；
  • sealed 的穷尽检查是编译期的，R8 不会改变它；
  • 但 R8 可能删掉”看起来没人用”的子类（如果只通过反射创建），需要 @Keep 或 keep 规则；
  • data object 的 toString() 在日志里可读，但混淆后类名可能变化，不要拿它做持久化 key。

5.5 else 的代价

在 sealed 的 when 里加 else，等于主动放弃”新增子类时编译报错”的保护：

只有在”这个 when 确实不关心未来新增类型”时才加，比如打日志兜底。灵江的 bindModule 加 else 是因为 HomeFeedModule 本来就不是 sealed，属于”类型事实”，不是偷懒。

5.6 嵌套层级别太深

SearchItem.CheckinItem 这种两层是舒服的；如果变成 A.B.C.D，调用方会很痛苦。领域模型建议”sealed 顶层 + 子类嵌套一层”，不要再往下套。

5.7 data object 的版本门槛

data object 需要 Kotlin 1.9。项目如果还在 1.8，写 object Loading : Row 即可，行为上单例语义一致，只是 toString 是默认的 Loading@hash。

六、面试考点（问答式）

Q1：密封类的本质是什么？

A：它不是一个”语法更好的枚举”，而是把一组有限的类型变体封闭在同一个包/模块里，并让编译器知道完整的直接子类清单。它带来两个能力：子类受限（外部不能随意扩展）和 when 编译期穷尽检查。它的价值在”新增变体时，所有需要处理的地方都被编译器点名”。

Q2：为什么 when 加了 sealed 就能穷尽？编译器怎么知道的？

A：sealed 的直接子类清单写在 Kotlin 元数据里。编译器编译 when 时读取这份清单，检查每个直接子类是否有 is 分支；全部覆盖就判定穷尽，不需要 else。编译产物是一串 instanceof 判断，不是反射。注意它只保证直接子类覆盖，孙子类通过父类的 is 分支一并覆盖。

Q3：sealed 的子类能不能放在别的文件？别的模块？

A：Kotlin 1.5 之前必须同文件；1.5 及之后必须同包、同模块，可以拆文件。跨模块绝对不行（直接子类）。间接子类（孙子类）不受限制。所以多模块项目里，sealed 基类要放在所有子类都能看到的公共模块，或者干脆别跨模块扩展。

Q4：sealed class 和 sealed interface 怎么选？

A：看子类是否需要共享状态/构造参数/protected 成员。需要 → sealed class；子类各自带不同数据、不需要共享字段、或者子类已经继承了别的类 → sealed interface。灵江 SearchItem 选 interface（五个 data class 各自持实体），HomeFeedNode 选 class（同一页面模型，未来可加共享行为）。

Q5：密封类和枚举什么时候可以互换？

A：满足这三个条件时枚举更合适：变体是固定单例、不需要携带不同字段、需要 name/ordinal/values/valueOf 或直接持久化。只要有一个变体需要”不同类型/不同数量的数据”，就该用 sealed。灵江的 DataType（纯标签）用枚举，SearchItem（每个变体带不同实体）用 sealed，WeatherAlertLevel（固定级别 + titleRes）用枚举。反过来，如果 sealed 的子类全是 object 且没有字段，可以考虑降级成枚举。

Q6：密封类和抽象类、普通接口的区别？

A：抽象类和普通接口是开放的，任何模块都能新增实现，所以 when 必须 else；sealed 是封闭的，编译器知道全集，所以能穷尽。抽象类可以有状态和模板方法，sealed class 也可以；关键差别不在”能不能有实现”，而在”实现范围是否受控”。灵江的 HomeFeedModule 是普通接口，所以 bindModule 不得不写 else。

Q7：泛型密封类怎么写？有什么坑？

A：sealed class Result<out T>，成功分支 Success<T>，失败/加载分支用 Nothing（Result<Nothing>），这样它们能赋给任意 Result<T>。坑有三个：out 的位置要对（协变位置才能用 out）；when 穷尽仍然成立，但泛型擦除让运行时无法判断 T；如果子类里出现 in T 的消费位置，协变会编译失败。

Q8：嵌套子类和平铺子类怎么选？

A：只在当前类内部使用的行模型，嵌套或 private 平铺都行；被多个文件引用的领域模型，建议 top-level sealed + 嵌套一层子类，命名清晰且作用域可控。Kotlin 1.5 之后不再强制同文件，但”同包同模块”仍在，所以拆文件可以，拆模块不行。

Q9：sealed 在序列化/混淆下有什么坑？

A：Gson 默认不记录子类信息，反序列化会丢字段，需要类型判别器；kotlinx.serialization 原生支持 sealed 多态，但要给每个子类加 @Serializable；Room 不能直接把 sealed 当 @Entity，通常存”类型标签 + 各实体表”；基于类名的多态在 R8 混淆下会断，需要 keep 规则；data object 的 toString 不要当持久化 key。

Q10：when 里加 else 有什么代价？什么时候可以加？

A：加了 else 就失去”新增子类编译报错”的保护，新类型会静默走兜底分支。只有在”这个分支确实不关心未来类型”时才加，例如日志兜底。灵江 bindModule 的 else 是因为 HomeFeedModule 不是 sealed；bindCatalog 的 when (node.type) 则是因为判的是 Int，编译器根本无法穷尽。

Q11：密封类为什么不能有子类在别的模块，但枚举可以跨模块用？

A：枚举的常量集合在编译期就固定，其他模块只是”使用”，不是”扩展”；sealed 的设计目标是允许”在本模块内定义有限变体”，跨模块扩展会破坏”编译器知道全集”这个前提。所以 sealed 的封闭范围必须和编译单元绑定。

Q12：sealed 有运行时开销吗？

A：几乎没有。when 编译成 instanceof 链，没有反射、没有 map 查找、没有枚举的 ordinal 映射表。分支很多时 JIT 也能优化。真正的成本是”每个子类是一个类”，会增加一点方法数和类数量，但在业务模型这个量级可以忽略。

七、一句话总结

密封类的本质不是”限制继承”，而是”用编译期已知的有限变体，换取新增类型时的全局编译检查”；选 sealed 还是 enum，取决于变体是”单例标签”还是”带不同数据的类型”。
