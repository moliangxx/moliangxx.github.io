策略模式：从灵江项目的类型分发说起

面试里问策略模式，很多人会背”Context、Strategy、ConcreteStrategy 三要素”。但真实项目里它往往不长这样：没有 Strategy 接口，只有一张 when 映射表；没有 Context 类，只有一个 Fragment。

这篇不写教科书，全部对照灵江项目 d:\AndroidProject\LingJiang 里实际存在的代码，讲清楚：什么情况下值得把 if-else 改成策略、Kotlin 里策略有哪几种落地形态、”新增类型只改一处”到底能改到多小、以及开闭原则的真实边界在哪。

一、场景：四个 tab 一套页面，六个分栏一套适配器

灵江首页有 4 个数据 tab（打卡 / 建筑 / 结构 / 文物），二级搜索页有 6 个分栏（综合 / 打卡 / 图鉴 / 结构 / 文物 / 用户）。如果按最直白的写法，会变成：

  • 4 个 HomeFeedFragment，每个里面复制一遍 RecyclerView 初始化 + Flow 订阅；
  • 6 个 SearchTabFragment，每个里面复制一遍适配器创建 + 空态控制；
  • 适配器里按 type 写 if-else，每加一种类型，改 3~5 处。

灵江的实际做法是：页面只保留一套，把所有”类型差异”收敛到一张映射表或一个 when 表达式里。这就是策略模式在业务代码里的真实形态——不是创建一个 Strategy 类，而是把”选择哪种行为”这件事集中到一个分发点。

2.1 DataShowFragment：枚举 + DataSpec 映射表

对应文件：main/mine/dataview/DataShowFragment.kt（下面节选了类型映射与订阅部分，省略 ViewBinding 和未登录兜底）。

页面只有一个，靠 arguments 里的枚举名区分”我的打卡”和”我的贡献”。差异（标题、空态文案、数据来源、点击行为）全部塞进一个 DataSpec：

几个值得注意的点：

  1. DataSpec 不是接口，是”数据 + 函数”的组合。source 是 (ArchViewModel, String) -> Flow<...>，bindClicks 是带接收者的函数类型 DataShowFragment.(HomeFeedAdapter) -> Unit。带接收者意味着在 lambda 里可以直接调用 open(...)、getString(...)，不用把 Fragment 当参数传进去。
  2. specOf 是唯一的选择点。生命周期方法（onViewCreated / initViews / observeData）里没有任何 when(type)，新增类型只需要在 specOf 里补一条。
  3. when 没有 else。DataType 是枚举，specOf 作为表达式返回 DataSpec，新增一个枚举值编译器会直接报错——这才叫”新增类型只改一处，而且漏改会编译失败”。

但它有一个真实缺陷，面试里可以主动提：最后一个分支是 else 而不是 M.TYPE_CHECKIN。新增 M.TYPE_XXX 时编译器不会报错，新类型会静默走”打卡”分支，最后表现为”数据串台”，而不是编译失败。类型安全的角度，这里应该写成 M.TYPE_CHECKIN -> ... 并让 when 穷尽——但 type 是 Int 常量而不是枚举，编译器无法穷尽检查，这才是根因。灵江用 M 里的 const val TYPE_XXX = 10/11/12/13，属于”用 Int 代替枚举”的典型代价。

三、原理拆解：策略模式的四个层次

3.1 策略的本质是”把选择和执行分开”

  • 选择：specOf(type) / when (type) / modules[slotIndex % size]；
  • 执行：spec.source(...) / bindXxx(...) / module.kind。

选择点越少越好。灵江里选择点基本都收在 specOf、getItemViewType、dataFlow、extractList、rowsOf 这五个函数里，页面生命周期方法里不再出现类型判断。

3.2 为什么不用一堆 if-else

不是说 if-else 有原罪，而是：

对比项 散落的 if-else 集中式策略分发
新增类型 改 N 个方法，漏改不报错 改 1 张表 / 1 个 when，枚举场景漏改编译失败
可读性 业务逻辑和类型判断混在一起 类型判断和业务逻辑分离
可测试性 必须构造整页才能测一个分支 specOf / dataFlow 可单独测
复用 每个分支一套页面 一套页面 + 多个策略
性能 分支多时仍有 JIT 优化空间 多一次间接调用，业务层可忽略

3.3 Kotlin 里策略的四种落地形态

形态 典型代码 编译期穷尽 可携带数据 新增类型的改动 适用场景
接口 + object/class interface HomeFeedModule + object WeatherModule 否 object 不能，class 可以 新增实现 + 注册 行为差异大、需要独立测试
枚举 + when enum class DataType + specOf 是（无 else） 枚举常量本身不携带 新增枚举值 + 补分支 类型有限且稳定
when 直接分发 getItemViewType / extractList sealed 是，Int 否 由节点/参数携带 补分支 UI/数据投影，轻量
函数类型 (T) -> R DataSpec.source、bindClicks 否 闭包可捕获 新增一条配置 策略即配置，逻辑很短
Map<K, (T) -> R> 通用写法：mapOf(TYPE_A to ::handleA) 否 闭包可捕获 新增 entry 策略数量多、需要动态注册

Kotlin 独有的一点：sealed class/interface + 无 else 的 when 表达式，等价于 Java 的访问者模式 + 编译器强制穷尽。HomeFeedAdapter 的 getItemViewType 就是靠这一点，新增节点类型时忘记处理会直接编译报错。

3.4 策略 vs 工厂 vs 简单分支

维度 简单分支 工厂 策略
解决的问题 当前这一处怎么走 对象怎么创建/选出来 行为怎么执行/替换
关注点 控制流 生命周期 + 依赖装配 算法/行为本身
灵江例子 buildFeed 里的 % 6 判断 DataShowFragment.newInstance(Type) 决定开哪个页面 specOf(type) 返回 DataSpec

一句话：工厂负责”给你哪个策略”，策略负责”拿到之后怎么干活”。specOf 严格说两者都沾，但因为它返回的是带函数的配置对象，业务收益主要在”执行”侧，所以按策略归类更准确。

四、坑与边界

  1. else 会吃掉新类型。HomeFeedData.dataFlow 用 else -> 打卡，新增类型不报错、静默走错分支。能用枚举/sealed 就不要用 Int 常量。
  2. Int 常量没有类型安全。M.TYPE_ARCH = 11 这类常量可以被随意传入 dataFlow，编译器无法约束。这是项目里真实存在的技术债，面试时可作为”如果重构我会怎么做”的素材：改成 enum class HomeType 或 @IntDef。
  3. 策略表放错作用域会泄漏。如果 DataSpec 里的 lambda 被放进 companion object 且在 lambda 里直接捕获 Fragment/Activity，页面销毁后策略表仍然持有引用。灵江的 DataSpec 在 companion object 里，但 bindClicks 用带接收者的函数类型，调用时才传入 this，不会在静态表里长期持有页面——这是正确写法。
  4. object 策略不能有可变状态。WeatherModule 是单例 object，如果给它加一个 var data，所有页面共享同一份状态，会串数据。需要状态就用 class 或把状态放到节点里。
  5. kind: String 不是类型安全的分发键。HomeFeedModule.kind 是字符串，两个模块写同一个 kind 不会报错。bindModule 里实际用 when (node.module) 按对象身份匹配，kind 只用于兜底展示，所以没出问题；但如果用 kind 做 when 分支，就要小心重复值。
  6. 过度策略化。一个只有两个分支、且永远不变的方法，抽成策略反而增加跳转成本。灵江没有把所有 when 都抽成接口，getItemViewType 仍是内联 when——这是合理的克制。
  7. 开闭原则不是”新增零改动”。灵江能做到的是”新增类型只改一处集中的映射表”，但枚举值本身、资源文案、适配器分支仍然要动。真正的 OCP 前提是”扩展点稳定”，业务类型天然会变，所以别拿”零修改”当验收标准。

五、面试考点

Q1：策略模式和一堆 if-else 的本质区别是什么？

不是”有没有 if”，而是选择逻辑是否被收口、行为是否可以独立替换。灵江的 specOf 把”选哪种数据源 + 注册哪些点击”收进一张表，生命周期方法里不再出现 type 判断；而一堆 if-else 会把类型判断散落在 onCreateView、observeData、onClick 里，新增类型时靠人肉搜索。策略模式真正的收益是变更半径可控 + 分支可单测，不是”看起来高级”。

Q2：策略模式和工厂模式怎么区分？项目里哪个是哪个？

工厂关注”对象怎么来”，策略关注”行为怎么执行”。DataShowFragment.newInstance(type) 负责创建页面并带上类型参数（工厂入口），specOf(type) 返回的 DataSpec 是策略（决定数据怎么查、点击怎么绑）。实际项目里两者经常混在一起，回答时别死抠定义，重点说清”选择”和”执行”两件事。

Q3：Kotlin 里为什么更推荐 sealed + when 做分发？

因为 when 作为表达式、且分支覆盖所有 sealed 子类时，编译器会做穷尽检查。HomeFeedAdapter.getItemViewType 新增一个 HomeFeedNode 子类，不补分支就编译失败。枚举也一样，前提是不写 else。灵江的 extractList 就是这种写法；而 HomeFeedData.dataFlow 因为用 Int 常量 + else，同样的错误不会在编译期暴露——这是反例。

Q4：when 里写 else 有什么风险？什么时候必须写？

else 会吞掉所有未覆盖的值，新增类型时静默归并到默认分支，问题从”编译失败”退化成”线上数据错乱”。只有两种情况该写：分支值域开放（如 Int 常量、外部传入的字符串），或者确实需要兜底降级（如 bindModule 里的 else -> node.module.kind）。能用枚举/sealed 的地方优先不写 else。

Q5：策略 vs 状态模式，怎么区分？

策略是外部选择：调用方根据 type 选一个行为，策略之间通常互不影响；状态是内部流转：对象自己根据当前状态切换到下一个状态，状态之间有时序依赖。灵江的 CatalogAdapter.switchTo(type) 是策略——由用户点击决定切哪个列表；如果改成”点一次自动轮换到下一个可用类型”，那就更接近状态机了。

Q6：函数式策略 (T) -> R 的代价是什么？

好处是配置化、代码短，DataSpec 里两个 lambda 就是典型；代价是：没有名字（栈里只能看到 invoke）、不能重载、调试断点不直观、闭包容易意外捕获大对象（比如整个 Fragment）造成生命周期泄漏。所以灵江只在”逻辑很短、只在一处使用”的场景用函数类型，复杂行为仍然落到独立方法或 object 上。

Q7：为什么把槽位插入逻辑放在 Adapter，而不是 Fragment？

因为”Banner 置顶 + 每 6 条插槽位 + 槽位轮换”属于列表的拼装规则，不是页面业务。放在 Adapter 内部后：页面只传原始数据 + Banner，四个 tab 都复用同一套规则；submitNodes 还能统一走 DiffUtil，槽位 id = "module_$slotIndex" 保证身份稳定。如果把拼装放在 Fragment，四个页面各写一遍，规则一改就要改四处。

Q8：如果让你重构 HomeFeedData.dataFlow，你会怎么做？

把 Int 常量换成封闭类型：要么 enum class HomeType，要么直接用 sealed interface FeedSource；dataFlow 的 when 去掉 else，让 M.TYPE_CHECKIN 显式成分支；HomeFragment.pageTypes 同步改成 List<HomeType>。这样新增类型时编译器会强制你处理，不会出现”新类型走打卡分支”的静默错误。前提是 M 里的常量还被其他模块大量使用，重构要控制影响面——这也是”开闭原则真实边界”的例子。

六、一句话总结

策略模式在业务代码里的真实价值，不是造一个 Strategy 接口，而是把”按类型选行为”的判断收口到最少的几个点，并让漏改在编译期暴露；灵江的 specOf 是正面样板，dataFlow 的 else 是反面教材。
