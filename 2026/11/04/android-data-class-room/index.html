数据类与存储策略：灵江的 data class、单表/拆表与 Room 幂等

这篇回答两个面试里经常被割裂的问题：

  • data class 到底替你生成了什么？为什么它不能 open/abstract？
  • 一张表什么时候该拆、什么时候该冗余？”幂等计分”只加一个唯一索引就够了吗？

灵江项目 d:\AndroidProject\LingJiang 正好把这两个问题连在一起：GrowthEvent 是成长流水（data class + Room 实体），CatalogUnlockPart 是图鉴解锁关系（唯一索引 + 幂等计分），AncientCheckin 是”单表内嵌游记 + 快照冗余”的典型。下面全部按真实代码（路径相对 app/src/main/java/com/lingjiang/）拆。

一、场景：一次打卡会写哪些表

用户在灵江打卡一次，可能发生：

  1. 写一条 ancient_checkin（打卡本体，含照片、地点、游记）；
  2. 关联 architecture_part（这座古建包含哪些结构/文物，属于知识层）；
  3. 写 catalog_unlock（谁解锁了什么，关系只增不改）；
  4. 写 catalog_unlock_data（解锁照片、感受等可变数据）；
  5. 写 growth_event（成长流水，userId + type + refId 幂等计分）；
  6. 更新 user 的 EXP/积分（汇总值）。

这六步里，哪些该合表、哪些该拆、哪些该冗余、哪些需要事务和唯一约束，就是”存储策略”。

2.2 AncientCheckin：单表内嵌游记 + 快照冗余

对应文件：data/arch/local/action/AncientCheckin.kt。

这段实体本身就是一份”存储策略说明”：

  • 游记不另起表：noteTitle/noteContent 内嵌在打卡表，避免”打卡表 + 游记表”两处编辑不一致；
  • 名称/省份/天气/节气做快照：列表和足迹统计不依赖联表，历史打卡保留当时的名称；
  • 照片列表用 List<String>：Room 通过类型转换器存 JSON，而不是再拆一张”照片表”。

2.3 CatalogUnlockPart / CatalogUnlockData：关系与数据拆表

对应文件：data/arch/local/part/CatalogUnlockPart.kt、data/arch/local/action/CatalogUnlockData.kt。

为什么拆成两张？

  • CatalogUnlockPart 是不可变关系（注释明确”只做创建，不可修改和删除”），适合放唯一索引、做幂等；
  • CatalogUnlockData 是可变数据（照片、感受、关联打卡会更新），生命周期和更新频率不同；
  • CatalogUnlockData 没有 userId，查询时通过关系表 JOIN，避免冗余用户字段（getUnlockDataByUserId 就是这么做的）。

2.4 ArchitecturePart：多态关系 + 复合主键 + 刻意不用外键

对应文件：data/arch/local/part/ArchitecturePart.kt。

文件头注释写得很清楚：

不使用 Room @ForeignKey 约束，避免用户行取号替换期间的外键报错，引用完整性由业务层保证（合并关系时若任一端实体解析失败，该条关系丢弃并记日志，不留悬挂绑定）。

这是一个有意的取舍：放弃数据库级引用完整性，换取”用户离线创建 → 云端全局取号 → 本地 id 级联改写”的同步流程不被外键卡住。

2.5 GrowthEventDao：REPLACE、幂等查询、Flow

对应文件：data/arch/local/action/GrowthEventDao.kt。

DAO 本身没有错：REPLACE 用于”同主键更新同步状态”，getByRef 用于应用层查重，Flow 用于列表订阅。问题在于表上没有 (userId, type, refId) 的唯一索引，而 getByRef 又是”先查后插”。

2.6 addGrowthEventOnce：应用层幂等 + 真实竞态

对应文件：data/user/UserRepository.kt。

这是典型的 check-then-act。单线程下没问题；但两个入口并发调用（比如”解锁成功”和”打卡成功”同时结算同一个 refId），都可能在 getByRef 返回 null 之后各自插入一条，导致重复加分。

项目还有一个结构性问题：GrowthEvent 表没有唯一约束，OnConflictStrategy.REPLACE 只对主键 id 生效，而两条流水的 id 是两个不同的 UUID，所以 REPLACE 拦不住重复。

2.7 unlockCatalog：唯一索引存在，但写入仍不是原子的

对应文件：data/arch/ActionRepository.kt。

catalog_unlock 有唯一索引，但 insert 用的是 REPLACE。仍有两种边界：

  1. 并发 check-then-act：两个调用同时 getByTarget 为 null，各自 insert。唯一索引会让第二次 REPLACE 删掉第一条再插入第二条，两条都返回 created=true，调用方可能给两次积分；第一条的 id 也会被替换掉。
  2. 多表写入无事务：catalog_unlock 插入成功、catalog_unlock_data 插入失败，会留下”有关系没数据”的半成品；再加上中间夹了 Bmob 网络请求，更不能把整个流程包进事务。

全项目没有使用 @Transaction 或 withTransaction（搜索无结果），这是当前存储策略的一个明确短板。

2.8 AppDatabase：版本 1、不写 Migration、允许主线程查询

对应文件：data/db/AppDatabase.kt。

DB_VERSION = 1 写在 base/M.kt，exportSchema = false，没有 Migration，也没有 fallbackToDestructiveMigration。项目当前的实际策略是：schema 变了就卸载重装。

2.9 类型转换器：List<String> / List<Int> 存 JSON

对应文件：data/db/ArchConverters.kt。

photos、imageKeys、galleryUrls 这些字段都靠它落成 JSON 字符串。好处是不用为”多图”再建一张子表；代价是JSON 内部不能建索引、不能按元素查询，解析失败时静默变成空列表。

2.10 Chat 的三个索引：有一个是冗余的

对应文件：data/ai/local/Chat.kt。

SQLite 的复合索引遵循最左前缀：(userId, conversationId) 已经能支持”按 userId 查询”，所以单独的 Index(userId) 是冗余的（会多一份写入放大和存储）。Index(conversationId) 不能去掉，因为复合索引的第二列单独查询用不上。

2.11 UserDao：同一个 DAO 里 Flow 和 LiveData 混用

对应文件：data/user/local/UserDao.kt。

两者都能响应 Room 的表变更，但：

  • LiveData 是 Android 生命周期感知的热数据，主线程观察，操作符少；
  • Flow 是冷流，收集才查询，操作符完整，需要 repeatOnLifecycle 管理生命周期。

3.2 只有主构造器属性参与

equals/hashCode/toString/copy/componentN 只覆盖 a，b 完全不参与。这是 data class 最常见的坑之一：把需要比较的状态写在类体里，DiffUtil 会认为两条数据”内容相同”。

3.3 copy 是浅拷贝

copy 只复制引用，不递归复制。对 List 来说，因为通常不改原列表而是 + 生成新列表，问题不大；但对可变对象/数组，修改副本会影响原对象。

3.4 == 和 equals

  • == 在 Kotlin 里就是 equals（空安全版本：a?.equals(b) ?: (b === null)）；
  • === 才是引用相等；
  • data class 的 equals 是结构相等，逐字段比较；
  • Array 的 equals 是引用相等（不是内容比较），List 才是内容比较。

灵江的 DiffUtil 就依赖这个语义：

== 比较的是整行业务字段（包括 photos、noteContent 这类大字段），所以列表刷新时可能做一次较重的深比较。

3.5 为什么不能 open / abstract / sealed / inner

Kotlin 规定 data class 不能是 abstract、open、sealed、inner，核心原因是生成成员必须有一致的语义：

  • 如果允许 open，子类可以增加状态、重写 equals，父类生成的 equals 对称性/传递性会被破坏；
  • copy 返回的是声明类型，子类复制会丢失子类字段；
  • componentN 的编号对应主构造器，继承后无法稳定扩展；
  • abstract 根本没有实例，谈不上”数据类”的相等与复制。

它可以实现接口、可以有伴生对象、可以有类体属性，但这些都不参与生成的五个成员。

3.6 可变 var + hashCode 的坑

GrowthEvent 用了 var，这带来一个经典风险：

实体类用 var 是为了 Room/同步回写方便，但不要把它当 HashMap/HashSet 的 key，也不要放进依赖 hashCode 的缓存。

3.7 Serializable 与 data class

AncientCheckin 实现了 Serializable，用于跨进程/Intent 传递。注意：

  • Serializable 依赖反射和 serialVersionUID，字段变化后反序列化可能失败；
  • List<String> 里的元素也必须可序列化；
  • Android 更推荐 Parcelable（@Parcelize），但 @Parcelize 要加在每个类上，且 data class 的 copy 不会自动处理 Parcel 逻辑（它只是普通对象复制）。

四、存储策略：多表还是单表

4.1 什么时候拆表

灵江的四个拆分理由，可以直接当判断清单：

场景 灵江案例 拆的理由
生命周期/可变性不同 catalog_unlock（只增不改） vs catalog_unlock_data（可更新） 不可变关系适合唯一索引/幂等，可变数据独立更新
多对多关系 architecture_part 一座古建包含多个结构/文物，关系需要独立行和复合主键
追加型流水 vs 汇总值 growth_event vs user.exp 流水可审计、可重放；汇总值只为读性能
避免超宽表/可选大字段 chat 与 conversation 分开 消息表行数大、写频繁，会话元数据独立

反过来，不该拆的情况：

  • AncientCheckin 的游记：内容源头只有一份，拆表会产生”两处编辑不一致”；
  • 多张照片：用 List<String> + 转换器足够，拆成 checkin_photo 子表会增加 JOIN 和同步复杂度；
  • 一对一且总是一起读写的数据：拆表只会多一次 JOIN。

4.2 什么时候冗余

灵江的冗余是快照式冗余，不是”为了省 JOIN 随便复制”：

它解决的是：

  • 离线列表不依赖古建表是否存在；
  • 古建改名后，历史打卡仍显示当时的名字；
  • 足迹地图直接按 province 分组，不用解析地址。

代价是更新异常：如果业务要求”改名后历史打卡同步改名”，快照就必须回填，否则数据不一致。所以冗余字段要明确语义：”这是当时的快照，不是实时值”。

4.3 唯一索引与幂等：正确做法

目标：同一 userId + type + refId 只允许一条成长流水。

第二步：插入用 IGNORE 或捕获约束异常，而不是先查后插。

这样”判重”和”插入”是同一个原子操作，并发下只有一条能成功。

第三步：多表写入用事务。

@Transaction 只能包住数据库操作，不能把 Bmob 网络请求包进去（否则长事务锁库）。正确顺序是：本地事务落库 → 提交 → 异步上云 → 失败置 PENDING 续传。

4.4 OnConflictStrategy 怎么选

策略 行为 适用 风险
REPLACE 删除冲突行再插入 同主键整行覆盖（同步回写） 本质是 delete+insert，可能改变 rowId/触发级联；对唯一索引会”顶掉”旧行
IGNORE 冲突时跳过，返回 -1 幂等插入、只增不改的关系 调用方必须检查返回值，否则以为插入成功
ABORT（默认） 冲突抛异常 需要明确失败的业务 要捕获 SQLiteConstraintException
@Upsert（Room 2.5+） 先插后更新，不删除行 需要保留 rowId/关联数据 需要实体可完整更新；不是所有场景都合适

灵江用 REPLACE 做”同主键同步状态回写”是合理的；但用它做”唯一索引幂等”就不合适，因为它会删除旧行，并让并发双方都以为自己是首次写入。

4.5 DB_VERSION 与 Migration 的取舍

灵江当前策略（如实记录）：

  • DB_VERSION = 1，exportSchema = false；
  • 没有任何 Migration；
  • schema 变更 → 开发机卸载重装；
  • 明确禁止 fallbackToDestructiveMigration，因为它会静默清库，掩盖问题。
维度 当前策略（卸载重装） 正式 Migration
开发速度 快，改字段不用写 SQL 每次改表都要写迁移、测试
数据安全 开发期数据全丢，可接受 用户数据保留
问题暴露 schema 不一致会直接崩，逼你面对 迁移写错可能悄悄丢数据/崩
上线可行性 不可用于正式版 必须
测试成本 低 需要 schema 快照 + MigrationTestHelper

利：项目还在字段定稿阶段，频繁改 schema，写 Migration 的收益低；卸载重装能保证每次都是干净 schema，避免”迁移掩盖坏数据”。

弊：

  • 一旦有真实用户，升级必须写 Migration，否则只能清数据；
  • exportSchema = false 导致没有 schema 历史，后续补 Migration 时没有基线可对比；
  • 开发期”卸载重装”的习惯容易延续到发布，风险很高。

合理的时间点是数据类定稿、准备发布前：把 exportSchema 改为 true，配置 room.schemaLocation，版本升到 2，补 MIGRATION_1_2，并加迁移测试。

4.6 Flow 查询与 LiveData 的差异

维度 Flow LiveData
冷/热 冷，collect 才查询 热，observe 才活跃
生命周期 手动 repeatOnLifecycle 自动感知
线程 查询在 Room executor，收集在调用方 setValue 主线程，postValue 任意线程
操作符 map/filter/combine/debounce 等完整 需要 Transformations/switchMap
背压 支持挂起/取消 只有”最后值”
适用 协程、复杂数据流 传统观察者、Java 互操作

灵江同时使用两者：UserDao 的 getUserById 还是 LiveData，而成长流水、会话列表、聊天记录都是 Flow。迁移方向应是 Flow，必要时用 asLiveData() 桥接旧 UI。

4.7 索引和外键

索引：

  • growth_event：userId、type、storageState 三个普通索引，支持列表过滤和同步扫描；
  • catalog_unlock：(userId, targetType, targetId) 唯一索引 + userId 普通索引。注意复合索引已经覆盖 userId 前缀，单独 userId 索引同样是冗余；
  • architecture_part：复合主键 + (childType, childId) 反查索引；
  • chat：(userId, conversationId) 复合索引已覆盖 userId，单独的 userId 索引冗余。

外键：

  • architecture_part 明确不用外键，原因是同步期间 id 会级联改写，外键会阻塞；
  • 不用外键的代价是可能出现悬挂引用，项目用”关系解析失败就丢弃 + 日志”兜底；
  • 如果业务稳定、id 不再变，@ForeignKey(onDelete = CASCADE) 能省掉大量手工清理，但要接受级联删除的风险。

六、坑与边界

6.1 data class 的 equals 包含所有主构造器字段

GrowthEvent 的 equals 会比较 remoteId、storageState、time 等所有字段。两个业务上”同一条流水”的对象，只要同步状态不同，== 就是 false。做 DiffUtil/去重时要想清楚：你要的是”业务相等”还是”整行相等”。

6.2 大字段参与 equals 的性能问题

AncientCheckin 的 photos、noteContent 可能很大，== 会逐项比较。列表刷新时如果 areContentsTheSame 直接比较整个实体，长列表会有明显开销。更稳的做法是比较轻量标识（id + version + updateTime）或在实体里维护 contentHash。

6.3 copy 不会自动更新 version

灵江在 updateCheckin 里显式 +1。如果忘了，云端合并会认为版本没变，覆盖逻辑失效。copy 只是复制，不会帮你做业务规则。

6.4 @PrimaryKey 的 String 默认空串

GrowthEvent、CatalogUnlockPart、CatalogUnlockData、AncientCheckin 的 id 都有默认值 ""。如果调用方忘了赋值，Room 会插入空串主键；第二条空串主键会被 REPLACE 顶掉，数据静默丢失。Chat 的 id 没有默认值，编译器会强制调用方传，反而更安全。

6.5 REPLACE 的语义不是”更新”

SQLite 的 INSERT OR REPLACE 在冲突时是删除冲突行再插入：

  • 可能改变 rowId；
  • 若定义了外键级联，可能触发删除；
  • 对唯一索引，会用新行”顶掉”旧行，旧行的 id 消失。

灵江没有外键，所以级联风险小；但在 catalog_unlock 上用 REPLACE 做唯一索引写入，会把”已存在”变成”替换成新 id”，调用方必须知道这一点。

6.6 先查后插在多入口下不可靠

addGrowthEventOnce 和 unlockCatalog 都是先 getByRef/getByTarget 再插入。只要有两个协程/两个进程入口并发，就可能都通过检查。应用层查重只能优化体验，不能保证幂等；幂等必须落在数据库约束上。

6.7 没有 @Transaction 的多表写入

unlockCatalog 先写关系、再上云、再写数据，中间任何一步失败都可能留下半成品；insertGrowthEvent 先写流水、再上云、最后更新用户汇总，进程被杀会留下”有流水、没加分”的不一致。

改进方向：

  • 本地多表写入用 @Transaction DAO 方法或 db.withTransaction { }；
  • 网络请求放在事务外；
  • 汇总值可以从流水重算（growth_event 本身是审计账本），启动时做一次对账。

6.8 allowMainThreadQueries() 是开发期便利，不是长期方案

AppDatabase 开启了主线程查询。虽然项目大多数 DAO 是 suspend/Flow，但一旦有人调用同步 DAO（比如 getUserByIdSync）在主线程，就会卡 UI。发布前应移除，靠协程/Room 的异步能力保证不阻塞。

6.9 exportSchema = false 的长期代价

没有 schema JSON，就没有迁移测试的基线。等数据定稿要写 Migration 时，只能靠人工回忆字段变化。建议在发布前改为 true，把 room.schemaLocation 配到 app/schemas，并纳入版本管理。

6.10 类型转换器的静默失败

ArchConverters.toStringList 解析失败时 getOrDefault(emptyList())，用户的多张照片可能”看起来还在数据库里，读出来却是空列表”。至少应该记录日志，重要数据不要在转换器里吞异常。

6.11 JSON 列不能索引

photos、imageKeys 存成 JSON 后，无法用 SQL 按图片 key 查”哪些消息引用了这张图”。如果这个查询是高频需求，就应该拆出 chat_image(chatId, imageKey) 子表并建索引。

6.12 冗余字段的更新异常

architectureName、province 是快照，不会随源数据自动更新。产品如果说”古建改名后历史打卡也要变”，就必须写回填逻辑；否则就把语义定清楚：”历史记录保留当时的值”。

七、面试考点（问答式）

Q1：data class 自动生成了哪些成员？

A：equals、hashCode、toString、copy、以及主构造器每个属性的 componentN。它们只覆盖主构造器里的属性，类体里的属性不参与。equals 是结构相等，hashCode 与之一致，copy 是浅拷贝且可选择性替换参数，componentN 支持解构声明。

Q2：data class 为什么不能 open/abstract？

A：因为生成的 equals/hashCode/copy/componentN 语义依赖”固定的主构造器字段集合”。允许继承后，子类可以增加状态、重写 equals，破坏对称性/传递性；copy 返回声明类型会丢子类字段；abstract 没有实例，谈不上数据相等。Kotlin 直接禁止这几种修饰，保证生成成员的一致性。

Q3：copy 是深拷贝还是浅拷贝？有什么坑？

A：浅拷贝。基本类型和不可变对象没问题；List、Map、数组、可变对象仍然共享引用。修改副本里的可变对象会影响原对象。灵江的 photos 用 + 生成新列表，所以相对安全；但 copy 不会自动递增 version 或更新业务字段，需要显式写。

Q4：== 和 equals 是什么关系？data class 比较时要注意什么？

A：Kotlin 的 == 就是空安全的 equals 调用，=== 才是引用相等。data class 的 equals 逐字段比较，所以两个”业务相同但同步状态不同”的实体会不相等；大字段（照片列表、长文本）参与比较会有性能开销；Array 的 equals 仍是引用比较，List 才是内容比较。

Q5：什么时候该拆表？什么时候该冗余？

A：拆表的信号：生命周期/可变性不同（关系只增不改 vs 数据可更新）、多对多关系、追加型流水 vs 汇总值、行太宽或可选大字段多。冗余的信号：读多写少且不想 JOIN、需要保留历史快照（名称/省份/天气）、离线可用。冗余的代价是更新异常，必须明确”快照还是实时值”。灵江把游记内嵌（单一数据源），把解锁关系和解锁数据拆开（可变性不同），把古建名/省份做快照（离线+历史）。

Q6：userId + type + refId 幂等计分怎么实现才可靠？

A：应用层先查后插不可靠，因为 check-then-act 在并发下会穿透。可靠做法是数据库唯一索引 + 原子插入：@Index(unique = true) 配合 OnConflictStrategy.IGNORE（返回 -1 判重）或捕获 ABORT 异常；多表写入再用 @Transaction。灵江当前只有 getByRef 先查后插，growth_event 没有唯一索引，多入口并发时可能重复计分，这是可以在面试里主动指出的改进点。

Q7：OnConflictStrategy.REPLACE 和 IGNORE、@Upsert 有什么区别？

A：REPLACE 冲突时删除旧行再插入，可能改变 rowId、触发外键级联，对唯一索引会”顶掉”旧行；IGNORE 冲突时跳过并返回 -1，适合幂等插入，但调用方必须检查返回值；ABORT 直接抛异常；Room 2.5 的 @Upsert 先尝试插入、冲突时更新，不删除行，适合需要保留 rowId/关联数据的场景。

Q8：DB_VERSION 和 Migration 应该怎么规划？灵江”卸载重装”的策略利弊？

A：DB_VERSION 是 Room 的 schema 版本，每次结构变更必须递增；正式项目要配 exportSchema = true、写 Migration、加迁移测试。灵江当前 version=1、exportSchema=false、没有 Migration，靠开发机卸载重装。利是迭代快、避免迁移掩盖坏数据；弊是丢数据、没有 schema 基线、习惯带到线上会出事故。合理节点是数据类定稿/发布前切到正式迁移。

Q9：@Transaction 解决什么问题？为什么不能把网络请求包进去？

A：@Transaction 保证一组数据库操作要么全成功要么全回滚，解决多表写入的半成品问题。但事务会持有数据库锁，网络请求耗时不可控，把网络包进事务会导致长时间锁库、并发下降甚至 ANR。正确做法是”本地事务落库 → 提交 → 异步上云 → 失败置 PENDING 续传”。

Q10：Room 的 Flow 和 LiveData 有什么区别？

A：Flow 是冷流，collect 才查询，支持完整操作符和协程取消，但需要 repeatOnLifecycle 管理生命周期；LiveData 是热数据，生命周期感知、主线程观察、只有最后值，操作符少。两者都能响应表变更。灵江 UserDao 还保留 LiveData，流水/聊天用 Flow，迁移方向是 Flow，旧 UI 可用 asLiveData() 桥接。

Q11：类型转换器有什么坑？

A：把 List<String> 存 JSON 的优点是免拆表，缺点是 JSON 内部不能索引、不能按元素查询，解析失败可能静默变空列表，大列表还会增加读写和比较成本。Gson 反射在 R8 下需要 keep 规则；如果”按图片 key 反查消息”是高频需求，应该拆子表而不是继续塞 JSON。

Q12：索引和外键该怎么设计？

A：索引按真实查询建，遵循最左前缀：(userId, conversationId) 已覆盖 userId 查询，单独的 userId 索引就是冗余；conversationId 单独查询仍需要自己的索引。外键能保证引用完整性、支持级联删除，但在”离线创建 → 全局取号 → id 改写”的同步流程里会阻塞，灵江因此不用外键，改由业务层校验并丢弃悬挂关系。

Q13：data class 的 var 属性有什么风险？

A：参与 hashCode 的字段被修改后，对象在 HashMap/HashSet 里的桶位置会失效，contains 可能返回 false。实体类为了 Room/同步回写常用 var，但不要拿它当哈希 key，也不要放进依赖 hashCode 的缓存；需要不可变语义时用 val + copy。

八、一句话总结

data class 用生成成员换来结构相等和复制便利，但只覆盖主构造器、只做浅拷贝；存储策略则要按生命周期/关系/读写模式拆表或冗余，而真正的幂等不能靠”先查后插”，必须落到唯一索引 + 原子写入 + 事务上。
