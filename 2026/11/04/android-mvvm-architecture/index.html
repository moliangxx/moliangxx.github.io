MVVM 与其他架构：灵江的 ViewModel 到底承担了什么

先纠正一个前提：你可能会听到”看 MainViewModel / BleDataViewModel 怎么拆分”——这两个类在灵江项目里不存在，它们属于另一个工程（LingYuan）。灵江实际存在的 ViewModel 是：

ViewModel 文件 类型 主要职责
ArchViewModel data/arch/ArchViewModel.kt AndroidViewModel 图鉴/打卡增删改查、图片落地、成长计分、系统图鉴解锁
ChatViewModel data/ai/ChatViewModel.kt AndroidViewModel 会话列表、发送消息、工具开关状态
SearchViewModel main/home/search/SearchViewModel.kt AndroidViewModel 五类内容搜索、防抖、综合混排
FindViewModel data/find/FindViewModel.kt ViewModel AI 出题、作答状态（纯内存）
BingViewModel data/bing/BingViewModel.kt AndroidViewModel Bing 每日壁纸
UserViewModel data/user/UserViewModel.kt AndroidViewModel 登录/注册/找回，返回 LiveData
LoginViewModel main/login/LoginViewModel.kt AndroidViewModel 登录后初始化与云端同步

首页的页面容器 MainActivity 没有 ViewModel，它只做 Fragment 栈和顶栏/底栏状态管理；数据全部由各 Fragment 自己拿 ViewModel。这篇就按这个真实结构讲。

二、灵江里的真实代码

2.1 ArchViewModel：AndroidViewModel + 仓库编排

对应文件：data/arch/ArchViewModel.kt。

几个可以拿来面试讲的设计点：

  • 写操作走 viewModelScope.launch(Dispatchers.IO)：ViewModel 不阻塞主线程，协程随 ViewModel 销毁自动取消；
  • 读操作分两种：持续变化的用 Flow（allCheckins / allArchitectures），一次性的用 suspend（queryArchitectureChildren）；
  • 业务编排在 VM，不在 Fragment：新增古建后要”落图 + 计分 + 解锁”，这三步顺序由 addArch 保证，页面不需要知道；
  • AndroidViewModel 持有 Application：为了拿 applicationContext 给 Room/ImageManager 用，属于”应用级 Context”，不是 Activity Context。

但它也暴露了一个真实问题：ArchViewModel 太大了。图鉴、结构、文物、打卡、计分、解锁、图片落地全在一个类里，接近 460 行。严格 MVVM 里它应该拆成 CatalogViewModel + CheckinViewModel + GrowthViewModel，或者把计分/解锁下沉到 Repository/UseCase。面试里被问”这个 ViewModel 有什么问题”，这是最好的切入点：职责过载，违反单一职责，测试时需要构造大量依赖。

2.2 ChatViewModel：StateFlow + 显式换流

对应文件：data/ai/ChatViewModel.kt。

值得逐条拆的细节：

  1. _xxx 私有 + xxx 只读：对外暴露 StateFlow，内部才持有 MutableStateFlow，页面无法 value = ... 直接改状态。这是单向数据流在类型层面的约束。
  2. stateIn(WhileSubscribed(5000))：没有订阅者 5 秒后停止上游查询，页面切走不空跑；5 秒内切回来还能复用。这是 Flow 转 StateFlow 的标准写法。
  3. lateinit var chatList + 显式 loadChatHistory：切换会话时换一条 Room Flow。注释里写得很清楚：不做自动换流，定位主对话/切换/新建会话后显式调用一次。换流是显式动作，不是隐式副作用——这比在 collect 里判断 conversationId 再 flatMapLatest 更好调试。
  4. try/catch/finally 兜底：AI 调用失败也要落一条”报错消息”，保证对话流不中断；finally 复位 isLoading，避免”永远转圈”。
  5. if (_isLoading.value) return：用状态本身做并发闸门，防止连续发送导致多条回复交错。

2.4 FindViewModel：不依赖 Android 的纯 ViewModel

对应文件：data/find/FindViewModel.kt。

它是纯 ViewModel，不持有 Application，只依赖 ChallengeAgent。这是最”干净”的一种：没有 Android 依赖，单元测试不需要 Robolectric。和 ArchViewModel 的 AndroidViewModel 形成对比——不是所有 ViewModel 都必须拿 Application，只有真的需要 Context 时才用。

2.6 Fragment 侧：viewLifecycleOwner + repeatOnLifecycle

对应文件：main/home/HomeFragment.kt、main/home/search/SearchTabFragment.kt、main/mine/dataview/DataShowFragment.kt。

这里每个词都有作用：

  • viewLifecycleOwner.lifecycleScope：协程绑定 Fragment 的 View 生命周期，onDestroyView 时自动取消；
  • repeatOnLifecycle(STARTED)：页面进入 STARTED 才订阅，进入 STOPPED 就取消订阅，回到 STARTED 重新订阅。后台不收集、不刷 UI；
  • collectLatest：新结果到来时取消上一次还在处理的收集体，避免”旧结果晚到覆盖新结果”；
  • _binding = null：ViewBinding 置空，防止 Fragment 实例比 View 活得久导致泄漏。

2.7 MainActivity：没有 ViewModel，只有页面栈

对应文件：main/MainActivity.kt。

MainActivity 承担的是导航和系统栏这类”平台职责”，不是业务状态。它没有 ViewModel 是合理的——不是每个 Activity 都必须配一个 ViewModel，只有需要跨配置变更保存业务状态时才需要。

三、原理拆解：MVC / MVP / MVVM / MVI

3.1 四种架构的数据流向

架构 数据流向 View 的角色 典型问题 灵江对应
MVC Model ↔ Controller ↔ View，三者互连 被动渲染 Activity 既是 Controller 又是 View，职责膨胀 早期 Android 写法，灵江已不用
MVP View → Presenter → Model，结果回调 Presenter → View 抽象成接口 接口爆炸、生命周期回调要手动解绑 无
MVVM View → ViewModel → Model，Model 通过 Flow/StateFlow 回推 观察状态 ViewModel 容易过载 ArchViewModel / ChatViewModel
MVI View → Intent → Reducer → State → View 只渲染 State 状态建模成本高、样板代码多 无（接近的是 SearchResult 聚合状态）

3.2 单向数据流（UDF）

单向数据流不是”数据只能往一个方向走”，而是：

  • 事件单向上行：UI 只发”意图”（点击、输入、提交），不直接改数据；
  • 状态单向下行：唯一可变的真相在 ViewModel/Repository，UI 只消费状态；
  • 状态不可变：_result.value = SearchResult(...) 整体替换，而不是改 SearchResult 内部字段。

3.3 ViewModel 与 LiveData / StateFlow / SharedFlow

维度 LiveData StateFlow SharedFlow
是否持有当前值 是 是（value） 否（默认无重放）
初始值 可无 必须有 无
订阅方式 observe(owner) collect（需生命周期控制） collect

灵江例子 UserViewModel.login()、UserDao ChatViewModel.isLoading、SearchViewModel.result WeatherAlertService.foregroundSignal

几个容易答错的点：

  • StateFlow 会去重：连续 value = 同一对象 不会重复发射。如果要做”每次都通知”，用 SharedFlow。
  • SharedFlow 适合事件：WeatherAlertService 用 MutableSharedFlow<Unit>(extraBufferCapacity = 1) 做前台信号，事件不该有”当前值”，新订阅者也不该收到旧事件。
  • LiveData 自带生命周期感知：这是它在老项目里最大的优势，但也是它和协程生态割裂的原因。

3.4 repeatOnLifecycle 与 viewLifecycleOwner

先看错误写法：

Fragment.lifecycleScope 跟的是 Fragment 生命周期，不是 View 生命周期。Fragment 被 hide / remove 时，onDestroyView 可能已经执行，但 Fragment 实例还在，协程继续持有 binding，就会操作已销毁的 View，甚至泄漏。

正确写法有两层保护：

  1. 作用域用 viewLifecycleOwner.lifecycleScope：onDestroyView 时取消协程；
  2. 收集用 repeatOnLifecycle(STARTED)：STOPPED 时停止收集，避免后台刷 UI 和浪费资源。

viewLifecycleOwner 和 this（Fragment）的区别，面试常问：

对比 this（Fragment） viewLifecycleOwner
生命周期 onCreate → onDestroy onCreateView → onDestroyView
何时销毁 Fragment 移除时 View 销毁时（可能更早）
多次 onCreateView 同一个 owner 每次重建都是新 owner
适用 只和 Fragment 本身有关的逻辑 所有和 View/binding 有关的订阅

SearchTabFragment 里还有第三种作用域写法值得注意：

六个分栏 + 父页面共享同一个 Activity 作用域的 ViewModel，因为它们要读同一份 result。如果写成 ViewModelProvider(this)，每个分栏会拿到独立实例，各查各的，结果就对不上。ViewModel 的作用域决定了状态共享范围，这是 MVVM 里很容易忽略的一点。

3.5 为什么 ViewModel 不能持有 View / Activity Context

  • ViewModel 的生命周期长于 Activity/Fragment 的 View（配置变更时 ViewModel 还在）；
  • 持有 View 会让已销毁的 View 无法回收，直接泄漏整棵视图树；
  • 持有 Activity 会泄漏整个 Activity，包括它的 Window、Drawable、FragmentManager。

灵江用 AndroidViewModel 拿的是 application.applicationContext，这是应用级 Context，生命周期和进程一致，不属于泄漏。注意 ArchViewModel 里还专门写了一句：

而不是直接存 application（虽然 Application 本身也是进程级，但显式取 applicationContext 更明确）。

四、坑与边界

  1. _binding 没置空。灵江所有 Fragment 都是 _binding + binding get() = _binding!!，onDestroyView 里 _binding = null。漏掉就是最典型的 Fragment 泄漏。
  2. Fragment.lifecycleScope 收集 UI 状态。必须换成 viewLifecycleOwner.lifecycleScope + repeatOnLifecycle。
  3. StateFlow 当作事件总线。StateFlow 会去重、会重放当前值，不适合”点一次弹一次 Toast”。事件用 SharedFlow 或 Channel。
  4. stateIn 的 WhileSubscribed 时间。ChatViewModel 用 5000ms，是为了页面短暂切后台再回来不重查；设成 0 会导致每次切页都重新查库，设得太大又会让上游长时间空跑。
  5. lateinit 的 StateFlow 未赋值就访问。ChatViewModel.chatList 注释明确写了”赋值前不可访问”，调用方必须先 loadChatHistory。这种”约定式安全”不如 val chatList: StateFlow<List<Chat>> = ... 可靠，但为了支持换流只能如此。
  6. ViewModel 里塞业务编排。ArchViewModel.addCheckin 里同时做了落图、写库、计分、解锁（解锁时还会生成 AI 日记），任何一步失败都会影响其他步骤。更合理的拆法是 Repository 提供原子操作，VM 只做”调用顺序 + 状态更新”。
  7. AndroidViewModel 滥用。不需要 Context 的 ViewModel（如 FindViewModel）就用普通 ViewModel，测试成本低很多。
  8. SavedStateHandle 缺失。灵江没有用 SavedStateHandle，页面参数统一走 Bundle（DataShowFragment.ARG_DATA_TYPE、HomeFeedFragment.ARG_TYPE、SearchTabFragment.ARG_TYPE）。这带来一个边界：进程被杀后，ViewModel 里的状态会丢，但 arguments 里的类型不会丢。所以”页面身份/类型”适合放 arguments，”用户输入/滚动位置”才需要 SavedStateHandle 或 onSaveInstanceState。
  9. onSaveInstanceState 与 ViewModel 的边界。onSaveInstanceState 只适合存少量、可序列化、重建 UI 必需的数据；ViewModel 适合存”配置变更期间要保留、但不需要跨进程”的状态。两者都不是数据库，不能替代持久化。
  10. MVI 的代价。MVI 要求所有状态收敛成一个不可变 State，所有操作收敛成 Intent。好处是可预测、易测试；代价是：状态类膨胀、每个操作都要写 reducer、简单页面也要一堆样板。灵江的 SearchResult 有点 MVI 味道（一个聚合状态包含六个分栏），但整体仍是 MVVM——没必要为了架构名词把简单页面复杂化。

五、面试考点

Q1：MVVM 和 MVP 的本质区别是什么？

MVP 里 View 通过接口回调接收 Presenter 的结果，Presenter 持有 View 接口；MVVM 里 View 观察 ViewModel 暴露的状态流，ViewModel 不知道 View 的存在。区别不在”有没有接口”，而在依赖方向：MVP 是 Presenter → View（双向依赖），MVVM 是 View → ViewModel → Model（单向依赖 + 状态回推）。灵江的 ChatViewModel 完全不知道 ChatAdapter 存在，只暴露 chatList / isLoading，这是标准 MVVM。

Q2：什么是单向数据流？灵江里怎么体现？

事件上行、状态下行、状态不可变。灵江的三处体现：_result / _isLoading 私有、对外只给只读 StateFlow；SearchViewModel 整体替换 SearchResult，FindViewModel.answer 用 map + copy 生成新列表；UI 只调 sendMessage、updateCheckin 这类意图方法，从不直接改数据源。

Q3：LiveData 和 StateFlow 怎么选？为什么灵江两种都有？

LiveData 自带生命周期感知、有 Java 互操作优势，但和协程/操作符生态割裂；StateFlow 是协程原生、可组合操作符、会去重，但需要自己配 repeatOnLifecycle。灵江的新模块（搜索、聊天、发现）统一用 StateFlow，登录模块沿用了 LiveData（UserViewModel.login 返回 LiveData<Boolean>，DAO 也有 LiveData<User>）。存量不重写、增量用新方案，是工程上更现实的选择。

Q4：StateFlow 和 SharedFlow 的区别？

StateFlow 有当前值、必须有初始值、会去重、新订阅者立刻收到最新值，适合 UI 状态；SharedFlow 默认没有当前值、不去重、可配置重放，适合一次性事件（Toast、导航、刷新信号）。灵江 WeatherAlertService 的 MutableSharedFlow<Unit>(extraBufferCapacity = 1) 就是事件用法；ChatViewModel.isLoading 是状态用法。

Q5：repeatOnLifecycle 解决什么问题？为什么不用 launchWhenStarted？

repeatOnLifecycle(STARTED) 在进入 STARTED 时启动收集、进入 STOPPED 时取消收集、再次进入时重新收集；launchWhenStarted 只是”挂起”协程，上游 Flow 仍在生产（如果是热流），资源不会真正释放，而且恢复时机和异常处理不如前者清晰。灵江所有页面收集都用 repeatOnLifecycle。

Q6：viewLifecycleOwner 和 Fragment 本身有什么区别？为什么不能用 requireActivity()？

viewLifecycleOwner 跟的是 View 生命周期（onCreateView → onDestroyView），Fragment 跟的是实例生命周期（onCreate → onDestroy）。Fragment 可能经历多次 onCreateView（比如 remove 后重新 add），每次的 owner 都是新的。用 requireActivity() 会让订阅活到 Activity 销毁，Fragment 的 View 已经没了还在收数据，直接崩溃或泄漏。灵江统一用 viewLifecycleOwner，连 FragmentResultListener 也绑在它上面（parentFragmentManager.setFragmentResultListener(..., viewLifecycleOwner)）。

Q7：ViewModel 为什么不能持有 View/Activity？AndroidViewModel 算不算违规？

ViewModel 在配置变更时存活，生命周期长于 Activity/View；持有它们会让已销毁的界面无法回收。AndroidViewModel 持有的是 Application，生命周期与进程一致，不算泄漏。灵江的 ArchViewModel 用 applicationContext 给 Room 和 ImageManager 用，是合理用法；如果它持有 Activity 去弹 Dialog，就是违规。

Q8：SavedStateHandle 和 onSaveInstanceState 的边界在哪？

onSaveInstanceState 存的是”重建 UI 必需、可序列化、数据量小”的内容（如滚动位置、临时输入），系统会把它交给新实例；SavedStateHandle 是 ViewModel 侧的同类能力，能在进程被杀后恢复 ViewModel 状态。两者都不适合存业务数据（该进数据库）。灵江没有用 SavedStateHandle，页面类型/实体都放 Bundle arguments——这类”页面身份”本来就该由导航参数承载，不需要 ViewModel 再存一份。

Q9：ViewModel 作用域是怎么决定的？灵江哪里体现？

ViewModelProvider(owner) 的 owner 决定作用域：ViewModelProvider(this)（Fragment）是页面级，ViewModelProvider(requireActivity()) 是 Activity 级，ViewModelProvider(singleActivity) 是整个 Activity 共享。灵江的 SearchTabFragment 六个分栏都用 ViewModelProvider(requireActivity())[SearchViewModel::class.java]，所以共享同一份搜索结果；HomeFeedFragment 用 ViewModelProvider(this)，每个 tab 各自持有 ArchViewModel/BingViewModel 实例。

Q10：MVI 的代价是什么？灵江算 MVI 吗？

MVI 要求状态不可变 + 所有操作收敛为 Intent + reducer 纯函数。好处是状态可预测、时序问题少、易测试；代价是状态类膨胀、样板代码多、简单页面过度设计。灵江整体是 MVVM：ChatViewModel 有多个独立 StateFlow，SearchViewModel 有一个聚合 SearchResult（略接近 MVI 的”单一状态”），但没有 Intent/reducer 这一层，所以不算 MVI。

六、一句话总结

灵江的 MVVM 不是”每个页面配一个 ViewModel”的模板，而是用 StateFlow 把可变状态收进 ViewModel、用 viewLifecycleOwner + repeatOnLifecycle 管住订阅、用 Repository 隔离数据源；ArchViewModel 的职责过载和 UserViewModel 的 LiveData 存量，恰好是面试里最值得展开的两个真实缺陷。
