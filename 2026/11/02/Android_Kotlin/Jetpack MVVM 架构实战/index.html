Jetpack MVVM 架构实战

很多教程把 MVVM 讲成三个缩写，但真正写起来，问题是：状态放哪、请求谁发、错误怎么回到 UI。这篇用一个“天气 + 收藏”的小项目，把链路走通。

一、分层与职责

层 只做一件事 不应该做
UI 渲染状态、转发事件 直接发网络请求
ViewModel 组合状态、处理业务编排 持有 Activity / Context
Repository 协调本地与远端 处理点击事件
DataSource 读写单一来源 决定缓存策略

二、定义 UiState

不要用一堆 Boolean 拼状态，用一个密封类表达“当前页面到底是什么样”。

Compose 里直接 when 分支即可，不会出现“loading 和 error 同时为 true”的尴尬。

三、Repository：单一数据源

关键点：Repository 是唯一能决定“先缓存还是先网络”的地方，ViewModel 不关心数据从哪来。

四、ViewModel：状态 + 事件

WhileSubscribed(5_000) 的作用是：页面不可见 5 秒后停止上游，回来时重新订阅，既省电又能拿到最新数据。

五、UI：只读状态，只发事件

UI 不持有 Repository，也不自己拼错误状态，测试时只需要传一个假 UiState。

七、常见误区

  • ViewModel 持有 Context：只允许 Application 级别，页面 Context 用 AndroidViewModel 也要谨慎。
  • 在 UI 里做缓存判断：那是 Repository 的职责。
  • 用 LiveData 和 StateFlow 混着写：新代码统一 StateFlow，老代码逐步迁移。
  • 把所有逻辑塞进 ViewModel：网络、数据库细节应该留在 Repository / UseCase。
  • 事件用 State 传：一次性事件（Toast、导航）用 Channel 或回调，不要塞进 StateFlow，否则旋转屏幕会重复触发。

八、小结

一条稳定的 MVVM 链路是：

把“状态”和“事件”分开，把“数据从哪来”关在 Repository 里，页面就会变得可测、可维护。
