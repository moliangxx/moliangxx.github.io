SharedPreferences

一、SharedPreferences 核心概念

SharedPreferences 是 Android 提供的 轻量级键值对（Key-Value）存储工具，用于持久化存储少量简单数据（如用户配置、登录状态、应用设置等）。

核心特点：

  • 存储形式：以 XML 文件格式存储在应用私有目录（/data/data/包名/shared_prefs/），安全且仅当前应用可访问。

  • 支持数据类型：仅支持 基本数据类型（String、int、float、long、boolean），不支持复杂对象（如自定义类、List、Map）。

  • 生命周期：数据随应用卸载删除，默认永久保存（除非手动清除或系统清理缓存）。

  • 适用场景：存储用户偏好设置（如夜间模式、字体大小）、登录状态（如记住密码）、临时配置（如上次浏览位置）等小体积数据（建议单个文件 。

与文件存储的区别：

特性 SharedPreferences 文件存储
存储形式 键值对（XML 文件） 二进制流（任意格式文件）
支持数据类型 基本数据类型 任意数据（文本、图片、视频等）
操作复杂度 简单（API 封装完善） 复杂（需手动处理流、文件）
查询效率 高（直接通过 Key 获取 Value） 低（需读取整个文件解析）
适用场景 配置类、简单键值数据 复杂格式、大体积数据

二、SharedPreferences 核心 API

SP 的使用流程分为 3 步：获取 SP 实例 → 编辑数据（通过 Editor） → 提交修改，核心 API 如下：

API 方法 作用 示例
getSharedPreferences(String name, int mode) 获取 SP 实例（name 为 XML 文件名，mode 为操作模式） getSharedPreferences("user_setting", MODE_PRIVATE)
getPreferences(int mode) 简化版：当前 Activity 专属 SP（文件名默认为 Activity 类名） getPreferences(MODE_PRIVATE)
edit() 获取编辑器（Editor），用于增删改数据 SharedPreferences.Editor editor = sp.edit();
putXxx(String key, Xxx value) 存储数据（Xxx 为数据类型，如 putString、putInt） editor.putString("username", "zhangsan");
remove(String key) 删除指定 Key 的数据 editor.remove("password");
clear() 清空所有数据 editor.clear();
commit() 提交修改（同步，返回 boolean 表示成功与否） boolean success = editor.commit();
apply() 提交修改（异步，无返回值，推荐使用） editor.apply();
getXxx(String key, Xxx defValue) 读取数据（defValue 为 Key 不存在时的默认值） String username = sp.getString("username", "");

关键说明：

  • 操作模式（mode）：仅推荐 MODE_PRIVATE（默认，仅当前应用可访问），其他模式（如 MODE_WORLD_READABLE、MODE_WORLD_WRITEABLE）已废弃（存在安全风险）。

  • commit() vs apply()：

    • commit()：同步执行，会阻塞主线程，返回布尔值表示提交结果（成功 / 失败）。

    • apply()：异步执行（后台线程），不阻塞主线程，无返回值，效率更高，是开发首选。

五、SharedPreferences 避坑指南

  1. 不要存储敏感数据（如密码、Token）：

  • SP 文件是明文存储的（XML 格式），直接存储敏感数据存在安全风险。

  • 解决方案：存储前用 AES 加密 数据，读取时解密（推荐使用 AndroidKeyStore 管理密钥）。

  1. 避免存储大量数据或复杂对象：

  • SP 是基于 XML 文件的，读取时会加载整个文件到内存，数据过多会导致内存占用过高、读取效率下降。

  • 解决方案：大量数据用 SQLite/Room 数据库，复杂对象用文件存储 + 序列化。

  1. 不要频繁提交修改：

  • 每次 apply() 或 commit() 都会触发文件写入，频繁操作会影响性能（如循环中存储数据）。

  • 解决方案：批量修改时，先通过 Editor 累积所有操作，最后一次提交：

  1. 注意线程安全：

  • apply() 是异步的，但 SP 本身不保证线程安全，多线程同时读写可能导致数据异常。

  • 解决方案：用 synchronized 关键字封装工具类方法，或使用线程安全的 SP 替代方案（如 Tencent MMKV）。

  1. 不要依赖apply()的提交结果：

  • apply() 无返回值，无法判断提交是否成功（如存储满时可能失败）。

  • 解决方案：若需要确保提交成功（如存储关键配置），使用 commit() 并检查返回值：

  1. Key 命名规范：
  • 建议用 “模块名_字段名” 命名 Key（如 user_username、setting_night_mode），避免不同模块 Key 冲突。
  1. 避免在主线程中读取大量数据：

  • 虽然 SP 读取效率高，但如果文件过大（如 >50KB），主线程读取仍可能导致 UI 卡顿。

  • 解决方案：大量数据读取放在子线程中，用 Handler 或 LiveData 回调结果。

六、SharedPreferences 替代方案推荐

如果 SP 无法满足需求（如线程安全、存储复杂对象、高性能），可考虑以下替代方案：

  • MMKV：腾讯开源的高性能键值对存储库，支持多数据类型、线程安全、加密存储，API 与 SP 类似，效率远超 SP。

  • DataStore：Google 推荐的 SP 替代方案，基于 Kotlin 协程和 Flow，支持类型安全、异步操作，无 SP 的线程安全问题。
